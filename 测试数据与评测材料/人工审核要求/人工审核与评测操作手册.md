# 人工审核操作手册

## 1. 本次审核的目标和边界

本手册用于冻结后的 50 组真实评测结果。每组 `case_001` 至 `case_050` 代表一个不同的学习者画像，不代表同一学习者的多个固定阶段。

本次人工审核与复核工作分为画像、事实、策略和动态闭环四类。四类结果均作为提交材料的一部分保存：策略复核56条中40条通过、16条不一致（50个阶段1加6个阶段2）；动态闭环复核18条全部通过，覆盖case_045~050，审核人均为审核人1。

| 审核表 | 审核对象 | 数量 | 对应比赛指标 |
| --- | --- | ---: | --- |
| `06_指标统计/personalization_review.csv` | Agent1 的当前阶段规划和 Agent3 的学习包是否共同适配该学习者 | 50 案例 x 5 项 = 250 条 | 学习者画像-资源难度适配准确率，目标 >=85% |
| `06_指标统计/fact_check_review.csv` | Agent3 学习包中的可核验技术事实 | 50 案例 x 3 条 = 150 条 | 专业知识错误率，目标 <5% |

原始证据和自动统计文件只读，不得直接修改：

- `02_50组个性化主评测/raw_outputs/` 中的原始输出、日志和题目；
- `strategy_review.csv`：Agent6 阶段策略复核表，共56条，审核人1复核，40条通过、16条不一致；
- `dynamic_loop_review.csv`：动态闭环复核表，共18条，覆盖case_045~050，审核人1复核，18条全部通过；
- `metrics_summary.json`、其他自动统计 CSV；这些文件由统计脚本生成；
- `simulated_is_correct` 等测试模拟字段；它们不是人工审核结论。

Agent6 的 56 个阶段决策另行自动统计：44 个案例完成阶段 1，6 个案例完成阶段 1 和阶段 2，共 `44 + 6 x 2 = 56` 个阶段闭环。它用于说明系统会依据答题反馈动态调整，不计入本手册的 250 条适配率分母。

## 2. 开始前检查

1. 在项目根目录打开本手册和两个 CSV，不要在副本中审核后忘记回传。
2. 确认 `raw_outputs/case_001` 至 `raw_outputs/case_050` 均存在；审核时只读这些文件。
3. 只填写审核表中的空白证据列、`verdict`、`reviewer_id` 和 `notes`。不得修改 `case_id`、条件编号、通过标准或证据路径。
4. `reviewer_id` 填审核员姓名或统一工号；每条都必须填写。审核日期和分歧处理记录在交付说明或团队指定的审核记录中保存。

### 每个案例的证据位置

以 `case_001` 为例，案例输入画像在：

`02_50组个性化主评测/evaluation_cases.csv`

案例输出在：

`02_50组个性化主评测/raw_outputs/case_001/stage_1/`

重点查看以下文件：

| 文件 | 用途 |
| --- | --- |
| `learner_profile.json`、`diagnostic_output.json` | 学习者基础、目标、盲区和前置知识 |
| `stage_planning_output.json` | Agent1 安排的知识点、难度、时长、学习路径和个性化说明 |
| `learning_package.md` | Agent3 生成的学习包、实训步骤、命令、代码和资源组织 |
| `assessment_questions.json` | Agent3 生成的阶段题目，用于判断学习包难度和知识点覆盖 |

## 3. 统一判定规则

所有人工审核表只允许在 `verdict` 中填写以下三种小写值：

| 结论 | 含义 | 指标计算 |
| --- | --- | --- |
| `pass` | 证据充分，符合该行的通过标准 | 计入通过数 |
| `fail` | 证据充分，但明确不符合通过标准 | 不计入通过数；事实表中计为错误 |
| `error` | 缺少必要文件/字段、生成失败，或无法根据可追溯证据判断 | 不计入通过数；事实表中计为错误 |

不能用 `not_reviewed`、`N/A`、中文结论或空白替代以上三种值。证据不足时填 `error`，不要猜测为 `pass` 或 `fail`。

`actual_evidence` 必须写可定位的真实证据，至少包含文件名、字段名或章节名和关键内容；`notes` 用于解释失败原因、替代抽样理由或存在分歧的地方。

示例：

`stage_planning_output.json: difficulty=初级，recommended_daily_hours=1.0；learning_package.md 的“环境准备”要求 CPU 安装并提供 Colab 备选。`

## 4. 画像与学习包个性化审核

打开 `06_指标统计/personalization_review.csv`。每个案例有 5 条，审核 Agent1 与 Agent3 的组合结果，而不是只看单个 Agent。

### 每一条的操作步骤

1. 在 CSV 中找到当前 `case_id` 和 `condition_id`。
2. 在 `evaluation_cases.csv` 查看该学习者的 `background`、`existing_skills`、`learning_goal`、`daily_hours`、`learning_style`、`hardware` 和 `expected_target_blocks`。
3. 打开该案例 `stage_1/stage_planning_output.json`，确认 Agent1 的阶段规划。
4. 打开该案例 `stage_1/learning_package.md` 和需要时的 `assessment_questions.json`，确认 Agent3 的学习包实际内容。
5. 在 `actual_evidence` 写出 Agent1 的字段值和 Agent3 的原文/章节；依据下表填写 `verdict`。
6. 填写 `reviewer_id`；有异常或边界判断时在 `notes` 说明。

### 五项审核标准

| `condition_id` | 通过 (`pass`) 的必要条件 | 应重点记录的证据 |
| --- | --- | --- |
| `target_path` | Agent1 的 `block_id/subtopic_ids` 与学习目标、已有基础和前置关系相符；Agent3 学习包覆盖该阶段的全部 `subtopic_ids`，不能只覆盖第一个知识点。 | 目标、当前阶段知识点、前置知识、学习包章节或练习对应关系。 |
| `difficulty` | Agent1 的 `difficulty` 与学习者基础相符，必要时说明前置补偿；Agent3 的解释、代码和练习难度不超出该阶段能力。 | 学习者基础、`difficulty`、前置补偿、学习包讲解和题目示例。 |
| `time_budget` | `estimated_hours`、`recommended_daily_hours`、`suggested_study_days` 与画像中的 `daily_hours` 相容；学习包工作量与计划相称。 | 每日可用时间、计划时长/天数、学习包任务量。 |
| `hardware` | Agent1 正确识别硬件限制；Agent3 的模型、参数、命令和实训步骤可在该硬件执行，或提供清楚、可执行的替代方案。 | 画像硬件、`hardware_notes`、模型/显存要求、CPU/云端替代方案。 |
| `learning_style` | Agent1 回应学习偏好；Agent3 的内容组织、解释方式和实操比例真实体现该偏好。 | 画像偏好、`learning_style_notes`、学习包的章节与练习安排。 |

判为 `fail` 的例子：无独立 GPU 的学习者被要求直接在本地以 24GB 显存运行，且没有替代方案；初学者被直接安排高级知识点且没有前置补偿；学习包遗漏了阶段规划中的一个知识点。判为 `error` 的例子：规划文件不存在、关键字段为空且学习包不能补足判断依据。

完成后应有 250 条记录，且全部为 `pass`、`fail` 或 `error`。正式学习者画像-资源难度适配准确率为：

`适配准确率（比例值） = pass 条数 / 250`

`适配准确率（百分比） = (pass 条数 / 250) x 100%`

例如 250 条中有 213 条 `pass`，则比例值为 `0.852`，即 `85.2%`，达到 `>=85%` 的目标。`fail` 和 `error` 都不计入 `pass`；两类结论的区别只用于保留失败原因。

## 5. 学习包技术事实核验

打开 `06_指标统计/fact_check_review.csv`。每个案例固定审核 `claim_index` 为 1、2、3 的三行，共 150 条。事实必须来自该案例的 `stage_1/learning_package.md`，不要审核题目、Agent4 的自动审核结论或案例输入本身。

### 每个案例如何选择三条事实

按以下顺序从学习包中选取三条不同类型、可被外部资料证实或证伪的技术主张：

1. 参数、版本或数值事实，例如显存要求、默认参数、版本兼容性；
2. 命令、代码行为或配置事实，例如某条命令的作用、训练参数的效果；
3. 性能、硬件、安全性或因果事实，例如量化对显存的影响、某配置的限制或风险。

某类事实确实不存在时，可从其他类补选，但必须在 `notes` 写明替代原因。不得选择“本课程分三步学习”这类无法证伪的教学描述，也不得为了方便只挑显然正确的陈述。

### 每一条的操作步骤

1. 在对应行的 `claim_text` 原样填入学习包中的一条完整技术主张；可保留必要的上下文，但不得改写其技术含义。
2. 在 `evidence_source` 填核验来源。优先顺序为：项目知识库原文或其来源链接、软件/模型官方文档、权威框架文档、岗位/行业规范。填写来源名称、链接或本地文件路径以及相关章节。
3. 将主张与来源逐项核对，在 `actual_evidence` 写出关键证据或版本条件。
4. 填写 `verdict`、`reviewer_id`。若来源之间冲突，在 `notes` 写明冲突和采用理由。

判为 `pass`：主张在适用版本、硬件和前提下与来源一致。判为 `fail`：主张与权威来源冲突，或遗漏必要前提而会导致错误操作。判为 `error`：没有可追溯来源、命令无法解析、文件或上下文缺失，无法可靠核验。

完成后应有 150 条记录，且全部为 `pass`、`fail` 或 `error`。正式专业知识错误率为：

`(fail 条数 + error 条数) / 150`

## 6. 交付前自检

1. `personalization_review.csv` 恰有 250 条数据行；`fact_check_review.csv` 恰有 150 条数据行。
2. 两张表中不存在空白 `verdict` 或 `not_reviewed`。
3. 每一行均填写 `reviewer_id`，每一条 `pass/fail/error` 都有可追溯的 `actual_evidence`。
4. 事实表的每个案例恰有 3 条主张，且抽样类型尽量覆盖参数/命令/性能或安全三个方向。
5. 不得编辑 `raw_outputs`、题目、学习包或自动统计结果；只交付两张完成的人工审核 CSV。

审核完成后，由项目负责人统一运行：

`python scripts/calculate_real_metrics.py`

该命令生成统计结果；审核员不应手工修改 `metrics_summary.json`。

## 7. Agent6 的说明（仅供理解，不需人工填写）

Agent6 在学习者完成当前阶段测试后，根据答题结果、知识点掌握状态和历史信息更新画像，并输出推进、巩固、简化、回退或结业等后续策略。下一阶段由 Agent1 使用更新后的画像重新规划，Agent3 再生成新的学习包。

本次人工审核不评价 Agent6 的策略对错。其 56 个阶段决策由自动测试单独统计，用来展示系统的动态闭环能力，不能混入 250 条画像-资源难度适配率，也不能代替人工事实核验。
