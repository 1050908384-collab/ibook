## 第一章：vLLM 的定位——为什么需要专门的推理引擎？

### 1.1 从训练到推理的鸿沟

你已经跑通了 DeepSpeed 分布式训练，知道怎么让模型“学会”。但部署是另一回事——训练关注**如何更新参数**，部署关注**如何快且省地服务用户**。

如果你直接拿 HuggingFace Transformers 做推理，会撞上三个坑：

| 问题 | 现象 | 原因 |
|------|------|------|
| **吞吐量低** | 单卡只能同时处理 1~2 个请求 | 每个请求独立计算，GPU 算力大量空闲等待 |
| **显存浪费** | 即使短请求也要为长请求预留最大长度显存 | 静态分配 KV Cache，按最大长度预留 |
| **延迟高** | 第一个 token 等待时间长 | 没有批处理机制，请求串行处理 |

**一句话总结**：Transformers 是为训练设计的，不是为高并发推理设计的。vLLM 就是专门来解决这三个问题的推理引擎。

## 块 2

**vLLM 核心价值与定位（动手版）**

训练好的模型不部署成服务，价值就出不来。vLLM 就是帮你把模型"上线"的工业级推理引擎，核心卖点两个：

1. **PagedAttention**：把 KV Cache 分页管理，消除显存碎片和过度预留——显存不够时尤其管用。
2. **Continuous Batching**：动态批处理，新请求随时插队进当前 batch，不用等上一批跑完。

效果：高并发下，相比朴素逐请求推理，吞吐量通常提升数倍到十几倍（官方评测常见"约一个数量级"，但具体倍数取决于你的模型、序列长度、并发量，**以自己场景实测为准**），同时延迟保持较低。

**动手验证**：先别装，记住一个判断标准——你的 GPU 显存建议 ≥16GB，且 CUDA 环境必须正确。下一章教你逐项检查。

**关键解读**：右上角的 `CUDA Version: 12.2` 是**驱动能支持的最高 CUDA 运行时版本**，它**不等于**你机器上装的 CUDA Toolkit 版本。要查看实际安装的 CUDA Toolkit 版本，需运行 `nvcc --version`。

原因在于 CUDA 有**次版本兼容性**：同一大版本内（比如都是 12.x），较新的 CUDA 12.x 运行时往往能在显示较低 `CUDA Version` 的驱动上跑。但跨大版本（比如 11.x 到 12.x）或驱动太旧，就可能不兼容。

**所以，记住这个判断逻辑**：

- `nvidia-smi` 的用途是**确认驱动已装好、GPU 可见**，别拿这个数字去精确判断能不能装某个 CUDA 版本的 vLLM。
- **能不能装，以 NVIDIA 官方驱动↔CUDA 兼容性矩阵和 vLLM 发行说明为准**。安装 vLLM 时，需确保 CUDA Toolkit 版本与驱动支持的 CUDA 版本兼容，且驱动版本不低于 CUDA Toolkit 要求的最低驱动版本。

**版本对应关系**（示意，具体以官方文档为准，且随版本更新会变）：

| 驱动支持 CUDA 版本 | 可尝试的 vLLM 安装方式 |
|---|---|
| 12.x | 优先选对应 CUDA 12 的预编译 wheel |
| 11.x | 需查 vLLM 发行说明确认是否支持 |

**本块学习检查**：运行 `nvidia-smi`，记录你右上角的 `CUDA Version` 数字，并对照 vLLM 官方发行说明确认该版本是否受支持。

## 4.4 KV Cache 显存怎么估算（重要）

别直接抄网上“某模型 KV Cache = 固定 X GB”的数字——那些结论往往没算对 GQA/MQA 的 KV 头数、层数、head_dim、缓存精度和序列长度，容易偏大或偏小。正确做法是先用公式估算，再和实测对照。

**单请求 KV Cache 字节数 ≈ 2 × 层数 × KV头数 × head_dim × token数 × 每元素字节数**

- 开头的 `2` 表示 Key 和 Value 各一份。
- **GQA/MQA 模型必须用 `num_key_value_heads`，不是 Query 头数**。很多模型 KV 头数远小于 Query 头数，用错会高估数倍。

**估算三步走：**

1. 打开模型 `config.json`，读 `num_hidden_layers`、`num_key_value_heads`（没有就用 `num_attention_heads`），用 `hidden_size / num_attention_heads` 算出 `head_dim`。
2. 代入公式，乘上你计划支持的最大序列长度和并发请求数，得到理论值。
3. 启动 vLLM 后，对照启动日志里实际分配给 KV Cache 的显存（以及可容纳的 token/block 数），**以实测为准**修正

## 块 17

## 6.1 为什么需要控制显存利用率？

vLLM 默认会使用 GPU 显存的 **90%** 来存储模型权重和 KV Cache。这个默认值在大多数情况下够用，但如果你遇到以下场景，就需要手动调整：

- **共享 GPU**：同一台机器上还有其他服务在占用显存，90% 的占用率会把别人挤爆
- **大上下文**：长序列推理需要更多 KV Cache 空间，默认比例可能不够
- **多模型**：同时加载多个 LoRA 适配器时，显存分配需要更精细

## 6.2 配置方法

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --gpu-memory-utilization 0.8 \
    --max-model-len 32768
```

**拆解一下这两个参数**：

- `--gpu-memory-utilization 0.8`：告诉 vLLM 最多用 80% 的显存，剩下 20% 留给其他进程。如果你独占 GPU 且不需要跑别的，可以保持默认（0.9）；否则建议调低
- `--max-model-len 32768`：限制模型能处理的最大序列长度。这个值设得越大，KV Cache 占用越多，超出显存就会 OOM。设小一点可以防止超长输入把显存打爆

**实操建议**：先跑默认配置，观察 `nvidia-smi` 的显存占用。如果 OOM，优先降 `--max-model-len`，再考虑降 `--gpu-memory-utilization`。

### 6.1 为什么需要控制显存利用率？

简单说，这是为了避免“显存爆炸”导致程序崩溃。大模型推理时，显存不仅要装下模型本身，还要留出空间给计算过程中的临时数据（比如 KV Cache）。如果让 vLLM 把显存全占了，一旦遇到峰值需求，就会直接 OOM（显存不足）。

**核心原则：留有余量。**

- **推荐范围 0.80~0.90**：`--gpu-memory-utilization` 参数用来控制 vLLM 能使用多少比例的显存。官方建议设置在 0.80~0.90 之间，既留出足够余量，又保证性能。**不要超过 0.90**，否则极易在推理峰值时触发 OOM；也不要低于 0.50，否则显存利用率过低会明显拖慢推理速度。

## 1.1 推理的本质：从“预测概率”到“选择 token”

大语言模型在推理时，每一步都会输出一个**概率分布**——即词表中每个 token 作为下一个词的可能性。比如输入“今天天气”，模型可能给出：

```
"很好"  → 0.35
"不错"  → 0.28
"真棒"  → 0.15
"糟糕"  → 0.08
...（词表中所有 token 的概率之和 = 1.0）
```

**生成策略**回答的问题只有一个：**从这个概率分布中，如何选出下一个 token？**

不同的选择方式，输出风格完全不同：

| 策略 | 核心行为 | 输出特点 |
|------|---------|---------|
| **贪心搜索** | 永远选概率最高的 | 确定、保守、可能重复 |
| **束搜索** | 同时维护多个候选，在有限束宽下优中选优 | 通常质量更高、计算开销更大 |
| **随机采样** | 按概率随机抽 | 多样、有创意、不确定 |

### 2.1 核心原理：Argmax 一条路走到黑

贪心搜索，规则就一条：**每一步，选当前概率最高的 token**。不回头，不考虑未来，只看当下。

**看个例子**（概率是假设的）：
- 第1步："今天天气" → 选"很好"(0.35) → "今天天气很好"

### 贪心搜索的优缺点

**优点（部署友好）：**

| 优点 | 对你的意义 |
|------|------|
| **强确定性** | 相同输入、相同配置下，输出稳定，方便调试和复现 |

## 束搜索的 `early_stopping` 三种模式

束搜索的核心是**同时维护多个候选序列**（束宽 `beam_width`），而不是像贪心搜索那样只盯一条路。`early_stopping` 参数决定**何时收手**，三种模式对应三种停止策略：

### 三种模式速览

| 取值 | 行为 | 特点 |
|------|------|------|
| `False` | 不提前停止，直到所有束都生成结束标记或达到最大长度 | 最严格，计算量最大 |
| `True` | 当至少 `beam_width` 个束生成结束标记时停止 | 较快，可能牺牲质量 |
| `"never"` | 不因束完成而提前停止，直到达到最大长度 | 最严格，计算量最大 |

### 推荐写法（新版 vLLM）

```python
from vllm import LLM
from vllm.sampling_params import SamplingParams

llm = LLM(model="Qwen/Qwen2.5-7B-Instruct")

sampling_params = SamplingParams(
    use_beam_search=True,
    beam_width=4,        # 同时维护 4 个候选序列
    max_tokens=100,
    early_stopping=False  # 不提前停止，直到所有束都生成结束标记或达到最大长度
)

outputs = llm.generate(
    prompts=["今天天气"],
    sampling_params=sampling_params,
)
```

## 4.1 为什么需要随机采样？

你之前学的贪心搜索和束搜索，都属于**确定性**策略——同样的输入，在相同配置下永远产生同样的输出。这在数学计算、代码生成这类需要唯一正确答案的场景下很合适。

但到了聊天对话、创意写作、头脑风暴这类场景，你希望模型每次给出不同的回答，而不是千篇一律。这时就需要**随机采样**策略，通过引入“随机性”来让输出多样化。

三种核心采样策略：

| 策略 | 核心机制 | 随机性来源 |
|------|---------|-----------|
| **Temperature 采样** | 对 logits 除以温度 T（T>0）后做 softmax | 温度越高，分布越“平坦”，随机性越强 |
| **Top-k 采样** | 只从概率最高的 k 个 token 中采样 | 限制候选池大小 |
| **Top-p（核采样）** | 从累积概率超过 p 的最小 token 集合中采样 | 动态调整候选池 |

理解这三者和贪心/束搜索的区别，是你做业务选型的基础。

你正在学习 vLLM 部署，目标很明确——把模型跑起来。但在敲命令之前，先想清楚一个问题：**你要模型给出"唯一正确答案"，还是希望它有多样性？**

这个选择决定了你后续所有参数怎么配。

### 第一步：先问"要不要确定性"

- **需要唯一正确答案**（比如翻译、摘要、数学题）→ 用**贪心搜索**或**束搜索**
- **需要多样性**（比如聊天、创意写作）→ 用**采样**

记住这个判断顺序，比死记参数名有用得多。

### 第二步：束搜索从 `best_of=2` 开始

如果你决定用束搜索，**不要一上来就设 `best_of=8`**——显存会爆炸。从 `best_of=2` 起步，跑通了再逐步加大。

**监控束搜索的显存**：`best_of` 增加会增大显存占用，因为需要同时维护多个候选序列，但具体增幅取决于序列长度和模型结构，建议监控实际显存使用。

### 第三步：`temperature=0` 就是贪心搜索的"开关"

这个对应关系比记 `use_greedy` 直观得多：**设置 `temperature=0` 时，模型输出变为确定性，等效于贪心搜索**。记住这一点，配置时不用查文档。

### 第四步：固定 `seed` 提升可复现性

在随机采样或混合 batch 场景下，建议设 `seed`，能提升同环境下的可复现性。

但注意：**`seed` 并不能消除跨版本、跨硬件的差异**。要跨环境对齐，还需固定框架/CUDA/GPU/并行配置等。别指望一个 `seed` 搞定所有复现问题。

### 经验取向速查

- **翻译/摘要** → 常用束搜索
- **聊天** → 常用采样

这只是常见经验，具体仍应结合任务与实测选择。

## 1.1 为什么需要随机采样？

上一章你掌握的贪心搜索和束搜索，都属于**确定性生成策略**——相同输入、相同配置，输出几乎总是相同。这在数学计算、代码生成、机器翻译里是优点，但在另一类场景里就成了硬伤：**多样性本身就是价值**。

| 场景 | 为什么需要多样性？ | 确定性策略的问题 |
|------|------------------|---------------|
| **聊天对话** | 同样的问候不应得到一模一样的回复 | 贪心搜索会让机器人像"复读机" |
| **创意写作** | 诗歌、故事需要不同风格和表达 | 束搜索输出单调、缺乏惊喜 |
| **头脑风暴** | 需要多角度、多思路的建议 | 确定性输出永远走同一条路 |
| **角色扮演** | 不同角色应有不同说话风格 | 温度太低会让所有角色"同一个声音" |

**核心理解**：随机采样不是"随便选"，而是**在高质量候选中引入可控的随机性**。它既避免了贪心搜索的单调，又不会像完全随机那样输出无意义内容。你即将学习的 Temperature、Top-k、Top-p 三个参数，就是控制这股随机性的三个旋钮——它们共同决定了"在多大范围内、以多不均匀的概率"去挑选下一个词。

**为什么这对你的 vLLM 部署目标很关键**：当你用 vLLM 部署模型时，`SamplingParams` 就是你在代码里控制这些旋钮的入口。理解这三个参数的含义，你才能针对不同业务场景（聊天、写作、代码生成）配置出合适的生成行为。

**Temperature：给 logits 做除法**

想象你在调一个“随机性旋钮”。Temperature（温度系数）的数学操作就一步：把模型输出的原始 logits（未归一化的分数）除以温度 T。

公式：
$$\text{adjusted\_logits}_i = \frac{\text{logits}_i}{T}$$

然后对调整后的 logits 做 Softmax，得到最终概率：
$$P(\text{token}_i) = \frac{\exp(\text{adjusted\_logits}_i)}{\sum_j \exp(\text{adjusted\_logits}_j)}$$

**直观效果**（这是你调参时的核心手感）：

- **T < 1（低温）**：logits 被“放大”，概率分布更“尖锐”，高概率 token 优势更明显，随机性降低。
- **T > 1（高温）**：logits 被“缩小”，分布更“平坦”，低概率 token 也有机会被选中，随机性增加。
- **T = 1**：不调整，用模型原始分布。

**4.1 核心原理：按累积概率动态裁剪**

Top-p 采样比 Top-k 更灵活：它不按“固定数量”裁剪，而是按“累积概率”裁剪。

**操作规则**：从概率最高的 token 开始累加，直到累积概率达到 p，只保留这些 token，其余丢弃。

- token_A: 0.30 → 累积 0.30
- token_B: 0.25 → 累积 0.55

- token_D: 0.10 → 累积 0.80

## 块 55

## 1.1 传统 KV Cache 管理的两大浪费

**先看问题本质**：大模型每生成一个新 token，都要把它的 Key 和 Value 向量存进 KV Cache。序列越长，KV Cache 越大，最终成为显存的最大消耗者。

**传统框架怎么做的？** 在 vLLM 之前，FasterTransformer、ONNX Runtime 等框架用**静态预分配**策略——为每个请求预先分配一块**按最大序列长度计算的连续显存空间**。

**举个具体例子**：假设模型最大上下文是 2048 tokens，某个请求实际只生成 50 个 token，传统框架照样给它预留能装 2048 tokens 的连续 KV Cache 空间。

**这导致两大浪费**：

**浪费一：预留空间远大于实际需求。** 绝大多数请求不会用满最大上下文长度，但显存已经按最大值锁死。上面例子中，2048 的空间只用了 50，剩余 1998 的空间完全闲置，白白占用显存。

**浪费二：显存碎片化。** 每个请求都要求**连续**的显存块，不同请求的 KV Cache 长度不同，分配和释放后会在显存中留下大量无法被有效利用的碎片空隙。这些碎片单独看都不大，但累积起来相当可观。

**一句话总结**：传统方案用"按最大值预留 + 连续空间"的方式管理 KV Cache，既浪费空间又制造碎片，在高并发场景下尤其致命——显存被大量无效占用，能同时处理的请求数大幅下降。

在静态预分配方案下，KV Cache 的显存管理存在两类典型浪费，直接制约推理性能：

## 1.2 PagedAttention 的核心洞察

PagedAttention 的核心，是把操作系统的**虚拟内存分页**思想搬到了 GPU 显存管理上。

### 调度器的“两步走”：先照顾老顾客，再迎接新客人

vLLM 的 Scheduler 就像一个精明的餐厅经理，每时每刻都在做同一个决策：**这轮“算力餐桌”上，该让谁先吃？**

它的核心逻辑很清晰，分两步走：

**第一步：优先“续餐”——处理正在运行的请求（Decode）**

想象一下，已经坐在餐桌上的客人（正在生成文本的请求）正等着上下一道菜（下一个 token）。Scheduler 会优先服务他们，保证低延迟。在代码里，它遍历 `running` 列表，每处理一个请求，就从“预算”（`token_budget`）里扣掉该请求的序列长度（`seq_len`）个 token。这一步确保了已开始的对话不会被冷落。

**第二步：有余力再“接新客”——处理新请求（Prefill）**

如果“预算”还有剩余，Scheduler 才会从 `waiting` 队列里迎接新客人。它会先看看这位新客人的“胃口”有多大（`get_prompt_len()`，即 prompt 的长度）。如果预算够，就一次性让它“吃个饱”（处理整个 prompt）；如果不够——即新请求的 prompt 长度超过剩余 token 预算——就**先让它吃一部分**，剩下的下一轮再补，这就是 **Chunked Prefill（分块预填充）**，避免新请求的“大胃口”堵住整条服务通道。

**为什么这么设计？**

- **Decode 优先**：保证正在生成的请求延迟最低，用户体验流畅。
- **Prefill 填充**：利用空闲算力处理新请求，提高资源利用率。

先记住一个核心结论：**Prefix Caching 的常态是“只读共享前缀 + 各写各的私有后缀 Block”，并不会每次生成都触发 Copy-on-Write。**

把场景拆开看，分两种情况：

**情况一：已缓存的完整前缀 Block → 只读共享**
多个请求共享同一段前缀 Block 后，这些 Block 保持只读，可以被多个请求安全共享，**不需要复制**。

**情况二：新生成的后缀 → 各写各的私有 Block**
每个请求继续生成时，新 token 写入**自己新申请的私有 Block**，天然互不影响。这一步本身**不需要 Copy-on-Write**。

1. 复制该共享 Block → 创建私有副本

### 从"能跑"到"能服务"：三个核心差距

**差距一：并发与吞吐。** 本地测试是单请求、串行处理，你等结果就行。生产环境是多个用户同时发请求，服务必须能**并发处理**，并且在高负载下保持稳定响应。vLLM 的 Continuous Batching 机制（你已学过）正是为此设计的，但要让它在服务模式下生效，需要显式配置。

- 显存分配不足 → 模型加载失败或 OOM（显存溢出）

**差距三：服务接口与稳定性。** 本地调用是函数调用，生产服务需要 HTTP 接口、请求排队、错误处理、多模型切换等能力。`vllm serve` 命令把这些能力内置了，但你需要配置参数来告诉它"服务怎么跑"。注意，默认端口 8000 在生产环境常被占用，建议使用 **10000+ 的高位端口**（如 `--port 10086`）避免冲突。

## 3.1 gpu_memory_utilization：显存使用的"总闸门"

这是 vLLM 部署中**最关键的显存参数之一**，它直接决定能留给 KV Cache 多少显存，进而影响最大并发数。

**作用**：限制 vLLM 可使用的 GPU 显存比例，取值范围 0~1。

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct --gpu-memory-utilization 0.9
```

**理解这个参数的关键**：

- 默认值 `0.9` 意味着 vLLM 把**该卡总显存 × 0.9** 作为自己的显存预算（用于模型权重 + KV Cache + 激活/CUDA Graph），而不是"在别人占用之外再额外拿 90%"
- 如果启动前这张卡已被其他进程占用较多显存，vLLM 按 `总显存 × 0.9` 计算的目标预算可能连权重都放不下，会直接**启动失败/报显存不足**——共享 GPU 时要把比例往下调，或先腾出显存
- 在权重占用固定的前提下，**调低这个比例主要是压缩留给 KV Cache 的空间**（降低可支持的并发/上下文），而不是"把模型权重变小"

**调参建议**：

| 场景 | 建议值 | 理由 |
|------|--------|------|
| 显存充裕、追求高吞吐 | 0.90~0.95 | 给 KV Cache 更多空间，支持更多并发 |
| 显存紧张、防止 OOM / 共享 GPU | 0.70~0.85 | 预留余量应对峰值和碎片，或给同卡其他进程让出显存 |
| 单卡硬塞大模型 | 需配合量化 + CPU offload | 调低本参数只压缩 KV Cache、不缩小权重；权重放不下要靠 `--cpu-offload-gb`/多卡 |

> **纠一个常见误区**：不要把"单卡跑大模型"简单等价于"把 `gpu_memory_utilization` 调到 0.35~0.5"。这个比例决定的是 vLLM 的显存预算目标，调低它

## 3.4 max-num-seqs 与 max-num-batched-tokens：并发控制的"双闸"

这两个参数就像推理服务的两道闸门，控制着每步能同时处理多少请求、多少 token。你正在做 vLLM 部署，理解它们能帮你精准调优显存和响应速度。

**第一道闸：`max_num_seqs`（调度上限）**

它限制单步最多同时调度多少条序列。注意：它不是启动时就全额预留 KV Cache，而是决定高并发时的峰值压力——并发越多、上下文越长，KV Cache 需求越大。显存紧张时，把它调小（如 8~64）能有效降压。

**第二道闸：`max_num_batched_tokens`（批处理上限）**

它控制 Chunked Prefill 的块大小，即每步最多处理的 token 数。小值（如 2048）让 Decode 更频繁，降低 ITL（首字延迟）；大值（如 16384）一次处理更多 Prefill，降低 TTFT（首 token 时间）。两者权衡，按你的响应需求取舍。

**关键提醒**：上表默认值仅为示例，vLLM 各版本会调整默认行为，**务必以 `vllm serve --help` 或所装版本文档为准**，别把某个数字当永久默认。

## 6.3 多卡部署的硬件要求

部署大模型时，单卡显存往往不够用，多卡并行是必然选择。但**不是把卡插上就能跑得快**——不同并行策略对硬件的要求差异巨大。

先看一张核心对照表：

| 并行策略 | 最低 GPU 数量 | 卡间带宽要求 | 网络要求 |
|---------|-------------|-------------|---------|
| 单卡 | 1 卡 | 无 | 无 |
| TP（张量并行） | 2 卡（需整除 head 数） | **很高**（强烈建议 NVLink/NVSwitch） | 优先单机；PCIe/跨节点可用但通信开销大，需实测 |
| PP（流水线并行） | 2 卡 | 中 | 跨机需 10Gbps+ |
| TP + PP 组合 | 4 卡+ | 组内很高、组间中 | 多机 InfiniBand |

**关键理解**：TP 每步都要跨卡同步，对卡间带宽极其敏感。所以**优先单机 NVLink/NVSwitch**。但注意——PCIe 或跨节点跑 TP 并非不可用，只是通信占比会明显上升。是否可接受，**以基准测试为准**，不要凭感觉说"没有 NVLink 就一定不能用 TP"。

## 第七章：常见问题与避坑清单

实战中你会遇到以下典型坑点，直接对照排查：

| 坑点 | 现象 | 解决方案 |
|------|------|---------|
| **OOM 启动失败** | `CUDA out of memory` | 降低 `--gpu-memory-utilization`（0.85→0.7）；减小 `--max-model-len`；使用量化模型（AWQ/GPTQ） |
| **抢占频繁** | 日志出现 `Sequence group X is preempted` | 增大 `--gpu-memory-utilization`（上限建议≤0.90，过高易引发OOM）；减小 `--max-num-seqs`；增大 `--tensor-parallel-size` |
| **多卡启动报错** | `Total number of attention heads must be divisible by tensor parallel size` | 确保 `tensor_parallel_size` 整除 `num_attention_heads`（如 32 头可切 2/4/8） |

## 6.3 多卡部署的硬件要求：从单卡到多卡的显存账本

你已经掌握了 vLLM 的两种部署方式——离线推理用 `LLM` API，在线服务用 `vllm serve`。现在进入实战中最容易翻车的环节：**显存预算**。多卡部署不是简单插上第二张卡就完事，核心是搞清楚"显存花在哪、怎么省、怎么分"。

### 先算一笔账：显存去哪了

部署时显存主要被三样东西吃掉：

1. **模型权重**——这是大头，但注意：`gpu_memory_utilization` 控制 vLLM 可用的总显存比例，调低会减少 KV Cache 可用空间，但若过低可能导致模型权重无法加载。
2. **KV Cache**——随上下文长度和并发数增长，是你能灵活控制的部分。
3. **激活值等运行时开销**——别忘了留余量。

**好习惯第一条：部署前先算显存预算**。权重 + KV Cache × 并发 + 其他，心里有数再动手。

### 四个关键参数，联动调整

| 参数 | 作用 | 调参要点 |
|------|------|----------|
| `gpu_memory_utilization` | 按"总显存×比例"设定显存预算目标，默认 0.9 | 共享 GPU 或防 OOM 时下调；调低主要压缩 KV Cache |
| `max_model_len` | 上下文硬天花板，直接影响 KV Cache 大小 | 短文本设 2048~4096，不超过模型声明最大长度 |
| `tensor_parallel_size` | 张量并行度，多卡部署大模型必需 | **必须整除模型的总注意力头数（所有注意力层的头数总和）** |
| `max_num_seqs` | 单步可调度的最大序列数 | 显存紧张时减小 |

**好习惯第三条：这三个参数一起调**——`gpu_memory_utilization`、`max_model_len`、`max_num_seqs` 互相影响，牵一发动全身。比如你调低 `max_model_len`，KV Cache 变小，就能提高并发数。

### 多卡部署：tensor_parallel_size 是关键

多卡部署大模型，`tensor_parallel_size` 是必设参数。它决定模型如何切分到多张卡上。**硬性约束：必须整除模型的总注意力头数（所有注意力层的头数总和）**，否则直接报错。

**好习惯第二条：从保守配置开始**。建议起步配置：`gpu-memory-utilization=0.85`、`max-model-len=4096`，确认稳定后再上调。
