## 2.1 最简命令：先学会跑起来

你的目标是 LoRA 微调，而微调的第一步不是写代码，而是**先学会看 GPU 的状态**。因为 LoRA 虽然省显存，但依然会 OOM（显存溢出）。学会用 `nvidia-smi` 看显存，是你微调路上的第一块垫脚石。

**最简命令只有一个：**

```bash
nvidia-smi
```

在终端里敲下这行命令，回车，屏幕上会立刻输出一个表格。这个表格就是 GPU 的“体检报告”。

**怎么读这张表？** 你不需要看懂所有列，先抓三个关键点：

1. **显存占用**：看 `Memory-Usage` 那一列，格式是 `已用 / 总量`。比如 `5120MiB / 8192MiB`，意思是你用了 5GB，总共 8GB。如果“已用”接近“总量”，说明显存快满了，再加载模型就可能 OOM。
2. **GPU 利用率**：看 `Util` 那一列，显示的是百分比。训练时这个数字应该很高（比如 80% 以上），如果很低，说明 GPU 在“摸鱼”，可能是数据加载太慢，或者代码没写好。
3. **进程列表**：表格下方会列出当前占用 GPU 的进程，包括 PID（进程号）和占用的显存。如果发现某个进程占着显存不干活，记住它的 PID，后面可以“杀掉”它来释放显存。

## 2.2 关键指标解读：训练时盯住哪两个数？

你跑 LoRA 微调时，`nvidia-smi` 的输出会有一大堆字段，但**真正需要你盯住的只有两个**：

| 字段 | 含义 | 你的判断 |
|---|---|---|
| `Memory-Usage` | 显存占用 / 总显存（如 128MiB / 32510MiB） | 接近上限 → 调小 **batch size** |
| `GPU-Util` | GPU 计算利用率（0% 空闲，90%+ 满载） | 长期很低 → 数据加载太慢，GPU 在空等 |

**怎么用？** 训练时如果显存快满了，先降 batch size；如果 GPU 利用率一直上不去，问题不在模型，而在数据读取速度。

**其他字段快速扫一眼即可**：
- `GPU 0`：多卡时的编号，单卡永远是 0
- `Name`：你的显卡型号（比如 RTX 4090）
- `Temp`：温度，过高说明散热有问题
- `Pwr:Usage/Cap`：当前功耗 / 最大功耗
- 进程区：看哪个 `PID` 在占用显存，确认是不是你的训练脚本

## 4.1 查看显存详情（①）

在 LoRA 微调中，显存是决定你能否跑起来的“硬门槛”。先用一条命令快速看清显存家底：

```bash
nvidia-smi -q -d MEMORY
```

输出会告诉你四件事：**总显存**（你手里有多少钱）、**已用显存**（已经花掉多少）、**空闲显存**（还能挥霍多少）、**显存类型**（GDDR6、GDDR6X、HBM2 等，不同代际速度差异很大）。

> **动手试一下**：运行上面命令，找到“已用显存”那一行。如果数字接近总显存，说明显存快满了——LoRA 微调前最好先腾出空间。

## 块 8

### 5.1 查看 GPU 进程

运行 `nvidia-smi` 后，看输出最下方的 **Processes** 区域，这里列出了正在占用 GPU 的进程。示例输出长这样：

```bash
+-----------------------------------------------------------------------------+
| Processes:                                                                  |
|  GPU   GI   CI        PID   Type   Process name                  GPU Memory |
|        ID   ID                                                   Usage      |
|=============================================================================|
|    0   N/A  N/A      12345    C   python3                         10240MiB |
+-----------------------------------------------------------------------------+
```

每一列的含义如下：

- **PID**：进程 ID。后面要释放显存时，杀进程就靠它。
- **Type**：进程类型。`C` 表示计算进程（比如 PyTorch 训练），`G` 表示图形进程。
- **Process name**：进程名称。
- **GPU Memory Usage**：这个进程占用了多少显存。

**动手试一下**：运行 `nvidia-smi`，看看当前有没有进程在占用 GPU。如果有，记下它的 PID 和显存占用，确认你能看懂每一列的含义。

## 块 9

**本块学习检查**：运行 `nvidia-smi`，找到占用显存但已无对应训练任务的进程 PID，用 `kill` 尝试结束它；若进程仍在，再用 `kill -9` 强制终止，并确认显存已释放。

---

你的 LoRA 微调脚本崩溃后，显存可能仍被“僵尸进程”占着——进程没退干净，GPU 内存不放。这会让后续训练报 OOM。手动清掉它：

1. 先跑 `nvidia-smi`，在输出里找到那个进程的 PID（比如 `12345`）。
2. 执行 `kill 12345`，温和地请它退出。
3. 如果它顽固不化，用 `kill -9 12345` 强制干掉。

## 块 10

## 6.1 导出监控日志——把GPU状态存成文件

你正在准备LoRA微调，训练可能要跑几小时甚至更久。盯着终端看显存变化不现实，所以这一节的核心就一句话：**让`nvidia-smi`自己记录，你只管事后看数据**。

### 先学会最简单的导出

```bash
# 每 2 秒采样一次，输出到 gpu_log.txt，按 Ctrl+C 停止
nvidia-smi -l 2 -f gpu_log.txt
```

跑起来之后，终端不会显示任何输出，数据直接写进文件。想看实时状态就另开一个终端，用`cat gpu_log.txt`查看。按`Ctrl+C`结束记录。

### 更推荐：导出成CSV格式

上面那种格式适合人眼直接看，但如果你想分析显存变化趋势（比如LoRA训练时哪个阶段显存峰值最高），CSV格式更方便——可以直接用Excel打开，或者之后用Python处理。

```bash
# 用 query 模式导出 CSV（更适合分析）
nvidia-smi --query-gpu=timestamp,name,memory.used,memory.total,utilization.gpu --format=csv --loop=1 -f gpu_log.csv
```

这条命令每1秒记录一次：时间戳、GPU型号、已用显存、总显存、GPU利用率。字段顺序可以自己调整，想加温度就加`temperature.gpu`，想加功耗就加`power.draw`——只要在`--query-gpu=`后面用逗号追加就行。

### 进阶：后台持续监控

CSV导出有个问题：如果训练跑8小时，你不可能一直开着终端。用`nohup`把监控放到后台，即使关闭终端甚至断开SSH，记录也不会中断：

```bash
nohup nvidia-smi --query-gpu=timestamp,memory.used,utilization.gpu --format=csv --loop=5 -f ~/gpu_monitor.csv > /dev/null 2>&1 &
```

拆开看这条命令：

- `nohup`：让进程忽略挂断信号，终端关了也不停
- `--loop=5`：每5秒采样一次（训练时间长，没必要每1秒一次，文件会太大）
- `-f ~/gpu_monitor.csv`：保存到home目录下，文件名`gpu_monitor.csv`
- `> /dev/null 2>&1`：把正常输出和错误信息
