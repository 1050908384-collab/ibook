### 2.1 需求分析与总体目标

系统的对象不是抽象的提问者，而是处于不同起点和不同资源约束下的实训学习者。输入层需要接收学习目标、已有基础、每日时长、学习偏好和硬件条件；过程层需要将这些事实转化为知识缺口、当前阶段和资源难度；结果层需要保留测试、审核和下一阶段策略，以支持学习过程回看。因此，系统形成以下需求：一是知识点级的诊断与阶段规划，二是与阶段相匹配的教程、代码、资源和题目组织，三是对生成内容的独立技术与教学质量审核，四是依据测评结果进行可解释的下一阶段决策，五是在模型服务异常时保持状态一致并明确降级结果。

总体目标是构建一个阶段式个性化实训闭环。系统不预先向学习者输出静态完整课程表，而是先生成当前可执行阶段；学习包通过审核后进入学习工作台；测试提交后由阶段决策更新掌握状态并决定巩固、推进或其他策略；仍存在知识缺口时再规划下一阶段。这样的设计使路径可根据当前学习结果调整，而不是把“推荐”停留在首次输入阶段。

### 2.2 核心思路与总体设计

系统采用“事实源约束 + 职责分离 + 状态驱动”的总体思路。学习者画像、知识目录、题库、资源目录和阶段状态均以结构化数据为优先依据；模型调用主要用于候选内的个性化表达、生成与解释，不替代事实源。学情诊断与阶段规划 Agent 处理“学习者是谁、当前应学什么”；个性化学习资源生成 Agent 处理“如何形成学习材料与答疑”；专业知识与教学质量审核 Agent 处理“内容是否准确、可用和适配”；学情评估与动态决策 Agent 处理“学习结果如何、下一步怎样调整”。

Orchestrator 负责将四类输出组织成会话状态：保存画像、阶段、学习包、审核痕迹、答题记录和阶段结果；控制生成—审核—修订循环；在云端调用失败时尝试本地模型或确定性逻辑；当无法得到可用结果时返回失败或人工复核状态，而不伪造成功。由此，系统的协同能力来自职责、输入输出和状态传递的实际分工，而非对单一模型调用的重新命名。

## 二、需求分析与总体设计

### 2.1 需求分析与总体目标

#### 2.1.1 功能需求

围绕大模型微调与推理部署的个性化实训场景，系统需要实现以下核心功能：

| 编号 | 需求名称 | 需求描述 |
|------|----------|----------|
| FR-01 | 学习者画像构建 | 通过结构化采集学习者基础、目标、时长、风格和硬件条件，生成可解释的学情画像与置信度评估 |
| FR-02 | 学情诊断与盲区定位 | 基于知识目录、别名匹配和语义召回，定位学习者知识盲区，低置信度时支持追问确认 |
| FR-03 | 知识点级阶段规划 | 基于知识图谱先修关系和掌握状态，动态生成当前学习阶段，包含阶段主题、预计时长和规划理由 |
| FR-04 | 个性化资源生成 | 根据画像、知识点和实训元数据，生成教程、实训代码、分阶实操指南和阶段测试题四种资源形态 |
| FR-05 | 专业知识审核 | 对生成内容进行技术事实、代码质量、行业规范、难度适配和认知负荷的结构化审核，支持多轮修订 |
| FR-06 | 实时答疑 | 学习过程中随时提问，系统结合当前阶段上下文生成回答并经过专业审核 |
| FR-07 | 阶段测试与判分 | 从题库中按知识点抽取测试题，支持客观题自动判分 |
| FR-08 | 学情评估与动态决策 | 综合测试结果、问答历史和学习行为，评估掌握状态并选择下一阶段策略 |
| FR-09 | 知识图谱可视化 | 展示知识网络、掌握状态和当前阶段位置，辅助理解整体学习路径 |
| FR-10 | 结业报告生成 | 所有目标知识点完成后，生成掌握度变化、学习时长和后续建议的结业报告 |

#### 2.1.2 非功能需求

| 编号 | 需求名称 | 需求描述 |
|------|----------|----------|
| NFR-01 | 专业准确性 | 最终生成资源中专业知识谬误率低于5%，关键技术陈述均可溯源 |
| NFR-02 | 个性化适配 | 画像—资源难度适配准确率不低于85%，核心知识点覆盖率不低于90% |
| NFR-03 | 系统容错 | 云端模型异常时自动回退至本地模型，保持会话状态和审核轨迹连续 |
| NFR-04 | 数据安全与隐私 | 用户画像和交互数据脱敏存储，API Key仅保存在环境变量中，不进入代码或日志 |
| NFR-05 | 可部署性 | 支持本地隐私模式、云端增强模式和混合容错模式三种部署方式 |
| NFR-06 | 领域可迁移性 | Orchestrator、审核追踪框架和前端工作台等通用能力可复用于其他垂直领域 |
| NFR-07 | 可追溯性 | 所有生成内容、审核意见和决策结果均保留完整Trace，支持回溯审计 |

#### 2.1.3 总体目标

作品的总体目标是将大模型从一次性问答工具，转化为能够理解学习者、规划学习路径、生成实训资源、把控专业质量并依据反馈持续调整的个性化实训基础设施。具体包括三个层面：

**个性化层面**，实现精准的学情诊断和动态路径规划——综合学习基础、学习目标、每日时长、学习风格和硬件条件，形成可解释的学习画像，并基于知识点级先修关系和实时掌握状态动态生成学习阶段。

**质量保障层面**，实现高保真资源生成和独立审核纠偏——结合专业知识库和实训元数据生成教程、代码、操作指南和测试资源，通过独立审核Agent对技术事实、代码质量、行业规范、难度和教学适配性进行多轮结构化审核。

**系统能力层面**，实现反馈驱动的阶段迭代和可容错运行——根据测试、问答和学习行为更新掌握状态并选择策略，同时支持云端模型、本地模型和确定性逻辑的多级容错，避免模型服务异常导致会话中断。

### 2.2 核心思路与设计原则

#### 2.2.1 核心思路

系统将复杂的个性化实训任务拆解为多个相互协作、职责边界清晰的Agent，分别回答学习过程中的四个核心问题：

- **学情诊断与阶段规划 Agent** 回答"学习者是谁、缺什么、当前应该学什么"；
- **个性化学习资源生成 Agent** 回答"应该给学习者什么内容、代码和练习"；
- **专业知识与教学质量审核 Agent** 回答"生成内容是否专业、可用、适配"；
- **学情评估与动态决策 Agent** 回答"学习结果如何、下一步怎么调整"。

Orchestrator作为协同编排中枢，将四个Agent串联成一个可恢复、可追踪的业务闭环，并将每个阶段的画像、知识点、资源、审核结果、测试结果和决策结果持久化存储。

这种职责切分的设计源于一个基本判断：生成与审核必须分离，避免"自审自证"；评估决策与生成分离，保证阶段推进依据的独立性。而诊断规划与评估决策分别负责学习的起点和终点，前者建立初始画像并规划路径，后者评估结果并调整方向，二者解耦使各自的输入输出更加清晰。

#### 2.2.2 设计原则

**事实源优先，生成受约束。** 学习者的身份、基础、目标和偏好来自结构化字段或明确输入；领域知识来自专业知识库；测试题来自经过整理的题库。大模型主要承担候选细化、个性化表达和解释生成，不替代事实源。生成内容必须绑定当前学习阶段、知识点和来源内容，系统优先基于知识块进行个性化处理，而不是让模型在无约束条件下自由创作。

**关键结论可追溯，决策过程可解释。** 重要技术陈述通过Claim绑定Source，并保留内容块、章节路径和原文位置。每个阶段返回阶段理由、前置条件、预计时长和策略说明，学习者能够理解为什么当前学习这个知识点，以及测试后为什么调整路线。

**异常不伪造，降级有保障。** 当云端模型、本地模型和确定性逻辑均无法产生可用结果时，系统返回明确错误或进入人工复核状态，不伪造看似正常的学习资源。云端模型异常时自动回退至本地模型，本地模型也不可用时使用确定性逻辑保障流程连续性，确保会话状态和审核轨迹不中断。
