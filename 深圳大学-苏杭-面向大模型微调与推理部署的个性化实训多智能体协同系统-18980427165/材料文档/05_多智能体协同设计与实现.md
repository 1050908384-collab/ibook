### 5.1 职责划分与协同机制

系统以职责分离而非角色数量作为协同设计原则。学情诊断与阶段规划 Agent 输出学习者画像、候选知识缺口和当前或下一阶段；个性化学习资源生成 Agent 基于阶段与知识内容生成学习包、代码或答疑，并组织题目与资源；专业知识与教学质量审核 Agent 对候选内容进行事实、规则、代码、难度和教学适配性检查；学情评估与动态决策 Agent 综合阶段正确率、答题记录和状态选择后续策略。Orchestrator 将前一环节的结构化输出作为后一环节输入，并保存中间状态，使协同结果可以按阶段回溯。

### 5.2 学情诊断与阶段规划 Agent

该 Agent 接收学习者目标、已有基础、时间、偏好和硬件等输入，结合知识目录、别名匹配、语义召回和图谱前置关系定位候选知识范围。其输出包括画像、知识缺口、置信度和阶段建议。低置信度时系统可要求补充信息；阶段选择受知识点状态和硬前置关系约束，而不是仅按用户目标关键词直接跳转。

### 5.3 个性化学习资源生成 Agent

该 Agent 接收当前阶段、知识点范围、学习者画像和检索内容，组织教程、代码片段、补充资源和阶段题目，并处理学习过程中的技术类问答。向量检索、文档分块查询、代码生成/处理、题目抽取和视频检索等能力按工具封装。模型生成是候选内容来源之一，受当前阶段、知识块和输出约束限制。

### 5.4 专业知识与教学质量审核 Agent

该 Agent 对学习包和技术问答实施统一审核，检查知识核验、规则一致性、代码问题、难度、认知负荷和风格适配。审核发现问题后，Orchestrator 将问题发回资源生成 Agent 修订；审核 Agent 再进行复核与裁决。该闭环的目标是保留问题、修订和复核痕迹，而不是声明所有生成内容天然无误。

### 5.5 学情评估与动态决策 Agent

阶段完成后，该 Agent 接收正确率、答题记录、当前画像和阶段状态，生成阶段总结并选择巩固、简化、推进或结业等策略。策略结果更新会话状态；若仍存在未掌握内容，Orchestrator 再调用规划链路生成下一阶段。题目判分与状态更新中包含确定性规则，不能误写为完全由大模型自主决定。

### 5.6 Orchestrator 协同编排中枢与 5.7 端到端流程

Orchestrator 负责会话建立、阶段切换、任务调用、审核循环、异常处理和数据持久化。端到端流程为：学习者输入→诊断与阶段规划→资源生成→专业与教学质量审核→学习与答疑→阶段测评→学情评估与动态决策→下一阶段规划或结业。云端模型调用异常时可尝试本地模型；模型能力均不可用时使用确定性逻辑保障可执行的状态流程，或返回明确失败与人工复核状态。

## 5. 方案书正式正文

## 五、多智能体协同设计与实现

多智能体协同是本作品的核心设计。系统没有采用单一大模型承担全部任务的模式，而是将个性化实训的完整流程拆解为四个职责明确、相互协作的运行时Agent，分别负责诊断规划、资源生成、质量审核和评估决策。各Agent拥有独立的输入事实、工具权限和输出契约，通过Orchestrator编排形成闭环。

### 5.1 职责划分与协同机制

#### 5.1.1 从三类业务角色到四个运行时Agent

赛题中的"学情诊断Agent、领域专家Agent、审核裁判Agent"是三类业务角色的概括。为了在工程实现中遵循单一职责原则，系统将学习前的诊断规划和学习后的评估决策拆分为两个独立的运行时Agent，最终形成四个真实运行时Agent。

| 业务角色 | 运行时Agent | 主要职责 | 在闭环中的位置 |
|----------|-------------|----------|---------------|
| 学情诊断角色 | 诊断规划Agent | 画像构建、盲区定位、知识点级阶段规划 | 学习起点 |
| 学情诊断角色的反馈决策扩展 | 评估决策Agent | 阶段测试评估、掌握状态更新、策略选择 | 学习终点（也是下一阶段的起点） |
| 领域专家角色 | 资源生成Agent | 教程、代码、实操指南、题目配置、实时答疑 | 学习过程 |
| 审核裁判角色 | 审核Agent | 专业知识、代码、规范、难度和教学质量审核 | 质量把关 |

这种拆分没有改变业务逻辑，而是将"学习前诊断"和"学习后决策"解耦，使每个Agent具有清晰的输入、输出和触发时机。生成与审核分离避免了"自审自证"，评估决策与生成分离保证了阶段推进依据的独立性。

#### 5.1.2 协同机制概述

四个Agent在Orchestrator的调度下形成一个完整的学习闭环：

1. **诊断规划阶段**：诊断规划Agent分析学习者输入，构建学情画像，定位知识盲区，并依据知识图谱生成当前学习阶段；
2. **资源生成阶段**：资源生成Agent根据当前阶段和学习画像，结合知识内容块生成个性化学习包；
3. **质量审核阶段**：审核Agent对学习包进行独立的专业技术审核和教学质量审核，通过结构化Issue推动多轮修订；
4. **评估决策阶段**：学习者完成阶段测试后，评估决策Agent综合评估学习结果，更新掌握状态，并选择下一阶段策略。

闭环的价值在于：每一阶段的学习结果都会反馈到画像和掌握状态中，进而影响下一阶段的内容选择、难度适配和路径规划。学习不是一次性交付的静态课程，而是一个持续迭代、动态调整的过程。

### 5.2 学情诊断与阶段规划 Agent

诊断规划Agent是学习闭环的起点，负责回答"学习者是谁、缺什么、当前应该学什么"。其核心挑战在于：如何从自然语言的用户输入中准确识别知识盲区，并给出合理的学习路径，同时避免模型自由发挥导致的路径错误。

#### 5.2.1 候选目录约束与置信度门控

开放式大模型容易将含义模糊的用户输入直接映射到错误的知识方向，尤其是目标领域、缩写和相近术语存在歧义时。例如，用户说"我想学大模型部署"，可能指服务化部署、模型量化压缩、推理引擎优化，甚至是模型训练后的导出流程——不同的理解会导向完全不同的学习路径。

为此，诊断规划Agent采用"候选目录约束 + 置信度门控"的机制：

**第一步：结构化事实提取。** 将用户输入拆解为身份、基础、目标、时长、风格、硬件等结构化字段，作为事实源。这些字段的可信度最高，是后续分析的基础。

**第二步：双路召回生成候选。** 对目标和基础进行两路召回：
- 别名精确匹配：用户提到的技术术语与知识目录中的别名进行精确匹配，命中率高但覆盖有限；
- 轻量中文语义召回：使用轻量级embedding模型对知识文档进行语义相似度召回，补充匹配遗漏。

两路召回的结果合并为候选目录集合。LLM只能在这个候选集合内细化知识盲区，不允许自由创造目录外的知识板块。

**第三步：置信度计算与门控。** 对诊断结果计算映射置信度。证据充分（多源召回一致、用户描述明确）则置信度高；证据不足、目录外目标或语义歧义则置信度低。当置信度低于门限时，系统不强行选择方向，而是主动向用户追问澄清。

这种设计将学情诊断从"模型自由猜测"转化为"目录约束下的证据驱动诊断"，用于降低初始路径错误风险及其对后续学习的影响。

#### 5.2.2 知识点级动态阶段规划

传统课程按章节或板块顺序推进，无法反映用户已掌握的知识，也不能根据阶段测试及时调整。诊断规划Agent采用"知识点状态 + 先修DAG"的动态规划机制：

**规划流程**分为三步：
1. 根据学习目标确定目标知识点，反向遍历硬前置关系，计算必修子图；
2. 查询用户各子知识点的掌握状态（`-1`未掌握 / `0`学习中 / `1`已掌握），跳过已掌握内容；
3. 识别所有已解锁知识点（即前置都已掌握的未掌握知识点），根据用户每日时长预算，选择一个或多个连续知识点组成当前阶段。

系统每次只生成当前一个学习阶段，而不是一次性规划完整课程表。这样设计可以避免用户因时间变化、测试失败或目标调整而导致后续内容全部失效。阶段生成返回阶段主题、预计时长、建议天数和规划理由，让学习者理解"为什么现在学这个"。

#### 5.2.3 关键设计原则

诊断规划Agent的设计遵循一个核心原则：**不让大模型直接决定学习方向**。LLM的角色是在召回得到的候选目录内做细化和解释，而不是自由选择知识板块。知识图谱和目录结构才是路径正确性的根本保障，模型只在结构约束内发挥语义理解和表达能力。

### 5.3 个性化学习资源生成 Agent

资源生成Agent负责回答"应该给学习者什么内容、代码和练习"。其核心挑战在于：如何在保证专业准确性的前提下，根据学习者画像和当前知识点生成真正个性化的学习资源。

资源生成使用的个性化输入包括：学习者年级（`grade`）、已有技能标签与已掌握知识点（`skill_tags`、`mastered_block_ids`）、学习目标及目标范围（`goal`、`goal_scope`）、当前目标板块和子知识点、每日可用学习时长（`daily_hours`）、学习风格（`learning_style`）、画像置信度与知识盲区（`confidence`、`knowledge_gaps`），以及用户设备信息（硬件描述、设备类型、GPU 型号、显存和 GPU 架构）。阶段测试正确率、错题分布、问答历史和学习行为作为后续阶段的反馈输入，用于调整下一次资源的难度、解释深度、练习量和实训方案。

#### 5.3.1 受约束的动态生成

本作品中的"动态生成"不是指所有内容都由大模型无约束地从零创作，而是指系统根据用户画像、知识点、阶段、设备和反馈，动态完成检索、选择、组合、改写和呈现。具体来说：

- **教程和实操指南**：基于知识内容块进行个性化改写，调整解释深度、代码复杂度和操作步骤的详略；
- **实训代码**：根据学习者基础和硬件条件调整参数，如Batch Size、量化配置、替代方案等；
- **测试题**：优先从经过整理和校验的题库中按知识点与难度抽取，不每次由大模型自由生成，保证测评结果的可靠性；
- **答疑内容**：结合当前阶段上下文检索相关知识，由大模型组织成自然语言回答。

生成过程以`knowledge_chunks`的内容块为最小单位。每个内容块独立生成、独立审核、独立修改，通过块的并行处理提升效率，通过块的顺序聚合保证最终学习包的结构完整性。

#### 5.3.2 块级并行生成流水线

学习包默认启用块级流水线。资源生成Agent按`knowledge_chunks`逐块进行个性化处理，并发上限按模型提供方配置，当前为云端 5、本地 3。每块生成完成后立即交给审核Agent独立审核，审核使用独立并发槽，不占用生成槽。

每个输出块保留：
- 来源文档和原文位置信息；
- 标题路径和内容版本号；
- 关键技术陈述的Claim标记；
- 关联的知识点和难度标签。

块级处理带来三个显著优势：第一，生成和审核可以并行，提高整体效率；第二，修改时只需要处理有问题的块，已通过的块不会被无意义重写；第三，审核问题可以精确定位到具体内容块，避免了"整包重写"导致的错误扩散。

#### 5.3.3 实时答疑能力

学习者在学习过程中可以随时提问。系统判断问题是否属于当前阶段技术问题，结合当前板块、子知识点和用户画像检索知识内容，由资源生成Agent生成回答，再经审核Agent审核后返回给用户。答疑记录也会保存下来，作为后续学情评估的辅助证据——例如，用户反复询问显存计算，可能说明其在量化和训练资源估算方面仍存在知识盲区。

### 5.4 专业知识与教学质量审核 Agent

审核Agent是系统质量保障的核心，负责回答"生成内容是否专业、可用、适配"。系统不声称在开放环境下能够实现理论意义上的绝对零幻觉，而是将"有效消除幻觉"落实为可检测、可追溯、可修正和可量化的工程机制。

#### 5.4.1 双维度审核能力

审核Agent同时具备专业技术审核和教学质量审核两个维度的能力：

**专业技术审核**聚焦内容的正确性和规范性：
- 知识库依据核验：检查技术陈述是否有知识库作为事实依据；
- 技术事实与参数检查：验证概念、参数、API描述的准确性；
- 代码语法和AST检查：通过静态分析检查代码语法错误；
- 受限环境代码执行检查：在受限沙箱中执行代码，检查运行时错误；
- 行业规范检查：检查是否违反微调、部署等领域的行业最佳实践；
- 技术Claim与Source绑定检查：确保关键技术陈述都有可追溯的来源。

**教学质量审核**聚焦内容的适配性和教学效果：
- 内容难度分析：评估内容难度是否与学习者基础匹配；
- 认知负荷分析：评估单位时间内的信息密度是否合理；
- 学习风格适配：检查内容呈现方式是否符合用户学习偏好；
- 步骤完整性：确保实操步骤完整、逻辑连贯；
- 实训任务可操作性：验证实训任务在用户硬件条件下是否可行。

双维度审核使得系统不仅关注"内容对不对"，也关注"内容适不适合当前学习者"，这是通用大模型无法做到的。

#### 5.4.2 Claim-Source绑定的块级审核辩论

审核机制是本作品最具特色的设计之一。系统将审核从"单向报错"升级为"结构化争议处理"，建立了"审核 → 答辩 → 复核 → 裁决"的完整闭环。

**核心机制是Claim-Source绑定：** 资源生成Agent在生成学习包时，为关键技术陈述建立Claim（可验证陈述声明），每个Claim绑定一个或多个Source（知识来源）。审核Agent围绕Claim进行核查，如果发现问题，则出具带来源的Issue。

**审核辩论流程**如下：

1. **首轮审核**：审核Agent逐块检查，对每个问题生成结构化Issue，包含问题编号、内容块编号、错误位置、错误类型、严重程度、相关Claim、相关Source和修改要求；
2. **生成Agent答辩与修订**：资源生成Agent收到Issue包后，逐条回复（accepted / rejected / partially_accepted），并对接受的问题进行修改，携带递增的版本号和修订说明；
3. **复核**：审核Agent对修改后的内容再次审核，确认问题是否解决；
4. **裁决**：Orchestrator对争议问题进行终审，决定是否通过或进入人工复核。

整个过程最多进行3轮。每轮只把仍未解决的问题重新列入问题列表，已经通过的内容块不会被重写。超过最大轮次仍有未决问题时，学习包标记为`needs_human_review`，可以降级展示给用户，但不进入正式知识沉淀。

审核过程的全部数据（来源清单、Claim声明、争议Issue、答辩轮次、各方回复）都持久化到审核追踪层的6张表中，以`trace_id`维度组织，确保审核过程全程可回放、可审计。

#### 5.4.3 审核的边界与价值

系统不声称实现了绝对零幻觉。审核机制的价值在于：

- **可检测**：能够发现的问题必须被发现，不让明显错误流入学习包；
- **可追溯**：每个问题都能定位到具体陈述和来源，不是模糊的"感觉有问题"；
- **可修正**：通过结构化辩论推动内容修订，问题有明确的修复路径；
- **可量化**：审核结果可以统计谬误率、修复率等指标，支持质量评估。

对于无法自动确认的问题，系统选择"不放行、不伪造"——进入人工复核状态，而不是强行通过一份可能有错误的内容。

### 5.5 学情评估与动态决策 Agent

评估决策Agent是学习闭环的反馈节点，负责回答"学习结果如何、下一步怎么调整"。它承上启下：上承当前阶段的学习结果，下启下一阶段的规划方向。

#### 5.5.1 学情评估

评估决策Agent综合多维度数据评估学习结果：

- **阶段测试正确率**：最核心的评估指标，直接反映知识点掌握程度；
- **错题分析**：分析错题对应的知识点和错误类型，定位具体盲区；
- **问答历史**：分析用户提问的频率、深度和关键词，推断理解困难点；
- **学习行为**：学习时长、阅读模式等行为信号，作为辅助评估依据。

评估完成后，Agent生成阶段总结，包含阶段正确率、掌握情况分析、错题原因定位和针对性的改进建议。阶段总结不仅告诉学习者"考了多少分"，更帮助理解"哪里没掌握、为什么没掌握、接下来怎么办"。

#### 5.5.2 策略选择体系

根据评估结果，评估决策Agent从六种策略中选择最适合的下一阶段策略：

| 策略 | 适用场景 | 后续动作 |
|------|----------|----------|
| `advance`（正常推进） | 测试达标，知识点掌握良好 | 推进到下一个已解锁知识点 |
| `challenge`（进阶挑战） | 测试表现优秀，当前内容偏简单 | 选择难度更高的知识点或增加拓展内容 |
| `reinforce`（巩固练习） | 正确率接近达标但有薄弱点 | 补充针对性练习，巩固当前知识点 |
| `simplify`（降维解释） | 正确率较低，理解有困难 | 提供更基础的解释，降低认知负荷 |
| `backtrack`（回补前置） | 错误根源在前置知识点 | 回退到相关前置知识点进行补习 |
| `finish`（完成目标） | 所有目标知识点均已掌握 | 生成结业报告，结束学习 |

策略选择不是简单的"正确率达标就推进"，而是综合考虑错题分布、问答历史和学习行为，选择最有利于学习者成长的路径。

#### 5.5.3 重要边界

评估决策Agent有一个明确的职责边界：它不重新推断或改写诊断规划Agent已经确定的板块映射、阶段知识点和映射置信度，只更新映射对象对应的学习状态和学习策略。这个边界保证了不同Agent对事实源不会产生冲突——诊断规划Agent负责"学什么"的事实判断，评估决策Agent负责"学得怎么样"的状态更新。

### 5.6 Orchestrator协同编排中枢

Orchestrator不作为第五个业务Agent，而是系统的调度和状态中枢，负责让四个Agent协同有序地运转。

#### 5.6.1 核心职责

Orchestrator的核心职责包括：

- 创建、恢复和结束学习会话；
- 统一组装各Agent的输入数据；
- 管理Agent之间的数据契约和流转；
- 控制内容块级生成和审核的并发数量；
- 处理块级任务完成事件和学习包聚合；
- 控制最大审核轮次和终止条件；
- 管理模型服务的回退和切换；
- 将中间结果和最终状态写入数据库。

#### 5.6.2 云端-本地-确定性三级容错

Orchestrator管理的三级容错机制是系统可靠性的重要保障：

```
DeepSeek云端主模型
        ↓ 超时、限流、请求失败或无有效正文
Ollama本地模型
        ↓ 两类模型均不可用
确定性流程兜底 / 明确错误 / 人工复核
```

三级容错的目标不是比较模型谁更强，而是保障：
- 会话状态不丢失——模型切换不影响已有的学习记录和审核轨迹；
- 已完成阶段不被回退覆盖——已经通过的阶段保持有效；
- 模型短暂异常时仍能继续流程——至少可以完成状态管理和确定性操作；
- 不可恢复时向用户明确说明——不以虚假内容掩盖服务失败。

这种设计体现了"异常不伪造"的原则：当系统无法产生高质量结果时，宁可明确告知问题，也不伪造一份看似正常的学习资源。

### 5.7 端到端业务流程

四个Agent在Orchestrator的调度下，共同构成了一个完整的端到端学习流程。

#### 5.7.1 流程总览

```
学习者输入
   ↓
诊断规划Agent → 画像构建 + 盲区定位 + 当前阶段
   ↓
资源生成Agent → 按块生成学习包
   ↓
审核Agent → 块级审核 + Issue反馈
   ↕ （多轮辩论修正，最多3轮）
学习包交付 → 学习者阅读 + 实时答疑 + 阶段测试
   ↓
评估决策Agent → 正确率计算 + 画像更新 + 策略选择
   ↓
规划下一阶段 或 生成结业报告
   ↺
```

#### 5.7.2 首次画像构建

学习者通过对话或表单提供学习基础、目标、时间、风格和硬件条件。诊断规划Agent提取结构化事实，进行知识目录匹配和语义召回，在候选目录内细化知识盲区，计算画像置信度。置信度达标后生成画像和当前阶段；置信度不足则主动追问澄清。

学习者看到的结果包括画像卡片、已有基础、知识盲区、学习目标、每日时长、学习风格、目标知识点、当前阶段主题、预计学习时长和阶段规划理由。

#### 5.7.3 学习包生成与审核

用户点击"开始学习阶段"后，Orchestrator将阶段信息和画像交给资源生成Agent。生成Agent从知识内容块中取得当前阶段相关内容，按块进行个性化生成，为关键技术陈述建立Claim。每块完成后立即交由审核Agent审核。

有问题的内容块进入结构化Issue包。生成Agent按块修改，修改完成后立即交由审核Agent复核。没有问题的块不进入修改队列，已通过的块不会被重写。所有内容块通过后，学习包状态为`approved`；超过最大审核轮次仍有问题的，标记为`needs_human_review`。

#### 5.7.4 学习、答疑与测试

学习者在学习过程中可以随时提问，系统结合当前阶段上下文生成回答并经过审核。阶段测试题以当前阶段对应知识点为约束，从专业题库中抽取组织。用户提交答案后，Orchestrator记录题目、答案、正误和答题耗时。

#### 5.7.5 阶段评估与下一阶段决策

阶段完成后，评估决策Agent综合阶段正确率、错题、问答历史、学习行为和当前画像，输出阶段总结与后续策略。用户确认继续学习后，Orchestrator调用诊断规划Agent重新规划下一阶段——而不是自动把预先生成的整套课程推给用户。

当所有目标知识点的掌握度都达到完成条件后，系统生成结业报告，包括掌握度变化曲线、总学习时长、各阶段正确率趋势、已完成知识点、最终能力清单和后续学习建议。
