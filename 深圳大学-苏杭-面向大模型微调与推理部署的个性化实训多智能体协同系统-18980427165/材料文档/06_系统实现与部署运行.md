## 3. 可直接放入方案书的正式文本

系统后端采用 Python 与 FastAPI，实现会话、诊断、阶段、答疑、测评、仪表盘和用户范围等接口。核心业务由 Orchestrator 统一编排，数据库通过 SQLite 保存知识与学习过程状态；向量检索路径和知识图谱文件与结构化数据共同构成知识服务基础。前端采用 React 与 TypeScript，构建产物可由后端在生产模式下托管。

部署时，系统读取 `backend/.env` 或进程环境配置模型、数据库、向量库和图谱路径。默认数据库配置指向项目根目录的 `data/sqlite_data/project.db`。首次启动检查种子数据、视频目录、学习材料和图谱文件，缺失时尝试执行初始化流程。云端模型默认配置为 DeepSeek，本地回退配置为 Ollama；确定性模式可用于不依赖生成模型的流程验证。上述回退机制保障的是流程连续与状态一致，不应被解释为所有内容质量在模型不可用时保持等价。

提交包已经配套源代码、依赖清单、前端锁定文件、环境变量示例、数据目录、图谱与测试目录。评审复现应优先使用提交包 `软件模块/部署说明.md`，并确认活动数据库为 `data/sqlite_data/project.db`。部署文档中的端口、依赖路径与代码配置必须在最终封装前再次逐项一致性检查。

## 六、系统实现与部署运行

本章介绍系统的技术实现方案、运行模式和部署方式。作品采用"设计与契约先行、最小闭环优先、数据规模化随后、评测驱动回补"的迭代开发方式，已完成从需求分析到系统联调的全部开发阶段。

### 6.1 技术栈与实施过程

#### 6.1.1 技术栈

系统各模块的技术选型如下：

| 模块 | 技术选型 | 作用 |
|------|----------|------|
| 前端 | React + TypeScript + Vite | 学习工作台、画像展示、知识网络可视化、阶段交互 |
| 后端 | FastAPI + Python 3.12+ | API服务、会话管理、阶段调度、问答和测试服务 |
| 编排层 | Orchestrator/Harness（自研） | Agent调度、状态维护、并发控制、审核轮次管理、异常回退 |
| 结构化存储 | SQLite | 业务状态、学习记录、审核追踪数据 |
| 向量检索 | ChromaDB | 知识内容向量索引和语义检索 |
| 知识图谱 | NetworkX | 知识点先修关系推理和阶段选路 |
| 云端模型 | DeepSeek | 主生成模型服务 |
| 本地模型 | Ollama (Qwen/DeepSeek) | 本地生成和云端故障回退 |
| 轻量Embedding | FastEmbed (bge-small-zh-v1.5) | 诊断规划Agent的中文语义召回 |
| 确定性逻辑 | Python业务逻辑 | 流程级兜底和状态一致性保障 |

选型遵循三个原则：一是与本地实训的部署形态匹配，SQLite等零额外依赖的组件优先；二是职责分离，结构化存储、向量检索和关系推理各用最适合的工具；三是为未来演进预留空间，如通过SQLAlchemy统一数据访问层，为后续迁移到PostgreSQL预留了接口。

#### 6.1.2 实施过程

作品从立项到版本冻结共经历六个阶段：

| 阶段 | 主要工作 | 关键产出 |
|------|----------|----------|
| 一、需求调研与领域界定 | 分析赛题要求；调研大模型微调与推理部署的技能培训场景；确定系统边界 | 需求清单、领域知识范围 |
| 二、系统设计 | 确定总体架构与Agent职责划分；定义数据库Schema、内容块结构、审核Issue结构等数据契约 | 架构设计、数据库设计、Agent接口契约 |
| 三、核心实现 | 实现四个Agent的Skill与工具、Orchestrator编排、前端学习工作台；基于最小种子数据跑通端到端闭环 | 可运行系统、垂直切片闭环 |
| 四、数据规模化 | 收集整理15个知识板块、73个知识点的文档与题目；完成内容切分、向量化与知识图谱构建 | 领域知识底座、向量索引与图谱文件 |
| 五、联调与校准 | 在全量数据规模下联调完整流程；校准检索范围、题目抽取与知识点覆盖；修复跨Agent数据流问题 | 稳定版本、校准记录 |
| 六、评测与冻结 | 执行完整案例、主评测与回退测试；统计核心指标；冻结代码、数据、Prompt与模型配置版本 | 测试报告、冻结版本 |

实施过程中的主要经验包括：契约先行降低联调成本——Schema和Issue结构在编码前定义，使四个Agent可以并行开发；数据规模化必须伴随参数校准——种子数据下调通的检索逻辑在全量数据下需要重新校准；评测驱动设计修订——主评测与回退测试直接推动了三级容错和审核辩论机制的完善；版本冻结纪律——代码、知识库、Prompt、模型配置与指标同版本冻结，保证全部证据可复现。

### 6.2 运行模式

系统支持两种运行模式，适应不同的使用场景：

**确定性模式**用于流程测试、接口测试和不依赖生成模型的闭环验证。阶段状态管理、规则检查和部分资源流程使用确定性逻辑完成，不调用大模型。该模式主要用于开发调试和自动化测试，确保在没有模型服务的情况下也能验证系统的流程正确性。

**混合模式**是正式演示和完整运行的推荐模式。状态管理、阶段推进和审核流程保持确定性，确保核心逻辑的稳定性；教程生成、答疑等自然语言内容由云端或本地模型生成，并由审核流程控制质量。混合模式兼顾了系统的可靠性和生成内容的丰富性。

### 6.3 部署模式

系统支持三种部署模式，适应不同的网络环境和隐私要求：

**云端增强模式**适合网络和API条件稳定的环境。由云端模型（如DeepSeek）提供主要生成能力，本地保存知识库、向量索引和业务状态。该模式的优势是生成质量较高，本地硬件要求较低；劣势是需要网络连接和API服务。

**本地隐私模式**适合需要数据不出域的高校或企业场景。使用Ollama本地模型和本地知识库完成全部生成和检索，所有数据都在本地处理。该模式的优势是数据安全、隐私可控；劣势是对本地硬件有一定要求，生成速度受限于本地算力。

**混合容错模式**是比赛展示和实际部署的推荐模式。云端模型作为主模型，本地模型作为回退模型，结合确定性逻辑和人工复核机制。该模式兼顾了生成质量和系统可靠性，即使云端服务短暂异常也能保持会话不中断。

需要特别说明的是：系统教授vLLM推理部署等内容，这是教学业务范围；系统自身的生成服务当前以DeepSeek/Ollama为主，这是系统自身的模型部署方式。二者分属不同层面——前者是"教什么"，后者是"用什么教"。

### 6.4 部署流程与边界说明

#### 6.4.1 部署流程

系统部署的主要步骤如下：

1. 安装Python依赖：`pip install -r requirements.txt`
2. 初始化主数据库：执行数据库初始化脚本
3. 构建知识向量索引：初始化ChromaDB向量库
4. 构建知识图谱：生成NetworkX图谱文件
5. 导入测试数据：加载题库种子数据
6. 启动后端服务：`cd backend && python main.py`
7. 启动前端服务：`cd frontend && npm install && npm run dev`

面向普通用户的发行包应预置向量索引和知识图谱文件，用户无需手动执行初始化步骤，开箱即可使用。

#### 6.4.2 部署边界说明

- 诊断规划Agent的轻量语义索引可以预先构建并随发行包提供，首次使用无需下载embedding模型；
- 资源生成Agent使用知识内容向量索引完成语义检索，首次部署需根据使用的embedding模型执行初始化脚本；
- 正式发行包不应在普通用户运行时隐式下载模型，所有模型依赖应明确告知用户；
- 数据库、向量索引和图谱版本需要与代码、Prompt和测试报告一起冻结，确保评测的可复现性。
