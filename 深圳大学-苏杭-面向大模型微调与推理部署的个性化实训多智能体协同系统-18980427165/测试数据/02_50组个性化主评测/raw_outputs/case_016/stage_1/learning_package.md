## 块 1

### 第一章：先搞清楚——我们到底在装什么？

你已经有 PyTorch 和 Transformer 的基础，目标是在 8GB 显存上跑 QLoRA 微调。那这一步环境准备，本质上是在给你的实验搭建一个“操作台”。很多教程会让你直接下载安装包一路点“下一步”，但那样装完你往往不知道装了什么、为什么装。这里先花 2 分钟理清三个核心概念，后面每一步你都能对应到自己的目标上。

**第一，Python 解释器。** 这是运行你写的 `.py` 脚本的“引擎”。你写的是高级语言，机器看不懂，解释器负责把它翻译成机器能执行的指令。你之后跑微调脚本、调用 HuggingFace 的 `transformers` 库，底层都是它在工作。你已经有 PyTorch 基础，对这个应该不陌生——只是这里要确保你装的是与后续 PyTorch / CUDA 版本兼容的 Python 版本，比如 3.10 或 3.11 这类常见搭配。

**第二，包管理器（pip 或 conda）。** 它负责安装、卸载、管理第三方库。你之后要装 `torch`、`transformers`、`peft`、`bitsandbytes` 这些 QLoRA 微调的核心依赖，全靠它。它的核心价值是“依赖解析”——你装 A 库时它自动帮你把 A 依赖的 B、C 库也装好，避免手动一个个找。

**第三，虚拟环境。** 这是最容易忽略但对你这种多项目并行的人最关键的。虚拟环境让你为每个项目创建一套独立的 Python 解释器和库集合，互不干扰。比如你在这个环境里装 PyTorch 2.x，在另一个环境里装 1.x，两者不会冲突。对 QLoRA 微调来说，不同项目可能依赖不同版本的 `transformers` 或 `bitsandbytes`，虚拟环境能让你随时切换，不用重装系统级 Python。

> **思考题**：如果你不建虚拟环境，直接在全局环境里装 QLoRA 相关依赖，之后另一个项目需要旧版 `transformers` 时会发生什么？这能帮你理解虚拟环境为什么是“专业工作台”的标配。

**完成本块后，请用自己的话说明：** 这块内容和你“在 8GB 卡上做 QLoRA 微调”的目标有什么关系？简单说，QLoRA 微调涉及多个库的协同工作（模型加载、量化、训练循环），环境搭建就是确保这些库能在你的机器上正确、隔离地运行。如果你在安装或理解过程中遇到任何解释不了的术语（比如“依赖解析”具体怎么工作），先记下来，之后在实操环节再提问。

## 块 2

### 1.1 Python 解释器：程序的"翻译官"

你已经熟悉 PyTorch 和 Transformer，对"代码需要被解释执行"这件事应该不陌生——但值得明确的是：你写的 `.py` 文件本质是文本，CPU/GPU 只执行机器指令。**Python 解释器**就是那个把 Python 源码翻译成底层指令的"翻译官"。没有它，你的训练脚本只是一堆文本，跑不起来。

### 1.2 代码编辑器（IDE）：你的"工作台"

记事本也能写代码，但效率极低。**IDE（集成开发环境）**提供语法高亮、自动补全、运行调试等功能，让你写代码像用 Word 写文档一样舒服。本文推荐两款：**VS Code**（轻量免费）和 **PyCharm**（专业强大）。做 QLoRA 微调时，你大概率会频繁修改脚本、查看日志，一个好用的 IDE 能省下大量时间。

### 1.3 虚拟环境：项目的"独立房间"

想象你同时在做两个项目：A 项目需要 `numpy 1.0`，B 项目需要 `numpy 2.0`。如果把它们都装到同一个 Python 里，就会冲突报错。**虚拟环境**就是为每个项目创建一个独立的 Python 空间，互不影响。本文使用 **conda** 来管理虚拟环境，它是目前最主流的方案。

**思考题**：你在做 QLoRA 微调时，大概率会用到 `transformers`、`peft`、`bitsandbytes` 等库。如果这些库的版本要求和你另一个项目冲突，虚拟环境如何帮你避免"装一个坏一个"的窘境？

**与学习目标的关系**：你要做 QLoRA 微调，本质上是在一个 Python 环境里跑训练脚本。解释器让脚本能执行，IDE 让你高效地改脚本，虚拟环境则保证 `transformers`、`peft`、`bitsandbytes` 这些依赖不会和你机器上其他项目打架——这三样是你搭好微调工作台的地基。

**记录**：如果遇到"解释器""IDE""虚拟环境"这些词中任何一个让你感到模糊的细节，先记下来，稍后提问。

### 2.1 Windows 用户

**第一步：下载安装包**

1. 打开浏览器，访问 https://www.python.org
2. 鼠标移到顶部菜单 **Downloads**，网站会自动推荐 Windows 版本（如 `Python 3.13.x`）。
3. 点击下载 **Windows installer (64-bit)**。

**第二步：运行安装程序（⚠️ 关键步骤）**

双击下载的 `.exe` 文件，弹出安装界面后，**务必做两件事**：

1. **勾选最下方的 "Add python.exe to PATH"**  
   这个选项把 Python 加入系统"环境变量"。不勾选的话，命令行里输入 `python` 会提示"不是内部或外部命令"，后续所有命令行操作都无法进行。

2. 点击 **"Install Now"**（默认安装）即可。  
   默认安装路径在 `C:\Users\你的用户名\AppData\Local\Programs\Python\Python313`，不含中文和特殊符号，避免后续路径报错。想改路径的话，务必确保路径中**没有中文或空格**。

**第三步：验证安装**

1. 按 `Win + R`，输入 `cmd`，回车打开命令提示符。
2. 输入以下命令并回车：

```bash
python --version
```

3. 如果显示 `Python 3.13.x`（或你下载的版本号），说明安装成功！
4. 再输入：

```bash
pip --version
```

如果也显示版本号，说明 Python 的包管理工具 `pip` 也一并安装成功了。


**思考题**：你之后做 QLoRA 微调时，`pip` 会用来安装 `transformers`、`peft`、`bitsandbytes` 等依赖包。如果安装时 PATH 没配好，这些包装完也无法在命令行直接调用——现在这一步勾选，省的是后面排查环境变量的时间。

**任务**：完成本块后，用自己的话说明"安装 Python 并配好 PATH"与"在 8GB 显存上跑 QLoRA 微调"之间的关系。如果遇到无法解释的术语（比如"环境变量"），先记录下来，下一节提问时一起解决。

## 块 5

### 2.2 macOS 用户

较老的 macOS 曾预装 Python 2.7，但 macOS Monterey 12.3 起已不再预装 Python 2；部分系统可能带有供系统脚本使用的旧版 `python3`。无论哪种情况，都强烈建议自行安装最新版 Python，避免直接依赖系统自带版本——尤其是你后面要做 QLoRA 微调，依赖系统旧版 Python 会在装 PyTorch 生态时埋下版本冲突的隐患。

**方法一：官方安装包（推荐新手）**

1. 访问 https://www.python.org，下载 **macOS 64-bit universal2 installer**（`.pkg` 文件）。
2. 双击运行，一路点击 "Continue" → "Install" 完成安装。
3. 打开终端（Terminal），输入验证：

```bash
python3 --version
pip3 --version
```

**为什么用 `python3` 而不是 `python`**：在现代 macOS 上，命令行默认并不提供 `python` 命令（早期版本曾指向系统自带的 Python 2，现已移除），系统与官方安装包统一使用 `python3`。因此请始终用 `python3` / `pip3`，避免踩到"命令不存在"或误用系统版本的坑。这条对你尤其重要——后续跑 QLoRA 脚本时，如果混用了 `pip` 和 `pip3`，装包的隔离环境会乱掉。

**方法二：Homebrew（适合已有 Homebrew 的开发者）**

如果你已经安装了 Homebrew（macOS 的包管理器），在终端执行：

```bash
brew install python
```

安装完成后，通常用 `python3 --version` 验证，但具体命令可能因安装方式而异，请以实际环境为准。


**思考题**：为什么官方安装包和 Homebrew 两条路径最终都统一用 `python3` 验证，而不是 `python`？想清楚这一点，能帮你避免在后续配置虚拟环境时踩到命令歧义的坑。

**与当前学习目标的关系**：这一步是 QLoRA 微调的环境地基。你已熟悉 PyTorch 和 Transformer，但 QLoRA 依赖 HuggingFace 生态（transformers、peft、bitsandbytes 等），这些库对 Python 版本有明确要求。用官方最新版 Python 而非系统自带版本，能确保后续 `pip install` 时依赖解析干净，避免在 8GB 显存上调试模型时还要回头排查环境问题。如果你在安装过程中遇到任何无法解释的术语或报错信息，先记录下来，下一步配置虚拟环境时一起解决。

## 块 6

### 2.3 Linux 用户（Ubuntu/Debian）

Linux 通常预装 Python，但版本可能较老——这对你要跑的 QLoRA 微调是个隐患，因为较老版本可能缺少新特性或与 PyTorch 的兼容性不佳。以下是 Ubuntu/Debian 系列的安装命令：

```bash
# 更新软件源
sudo apt update

# 安装 Python 3 和 pip
sudo apt install python3 python3-pip python3-venv -y

# 验证
python3 --version
```

**为什么这样写**：`-y` 参数表示自动确认安装，不需要你手动输入 `y`。`python3-venv` 是创建虚拟环境所需的模块，一起安装避免后续补装。

**与学习目标的关系**：QLoRA 微调依赖 PyTorch 及 HuggingFace 生态工具链，而这两者都需要一个干净、版本可控的 Python 环境。本块确保你有一个可用的 Python 3 和 pip，这是后续创建虚拟环境、安装依赖（如 `transformers`、`bitsandbytes`）的前提。你已熟悉 PyTorch，应该清楚环境隔离对避免依赖冲突的重要性——`python3-venv` 正是为此服务的。

**思考题**：为什么在 8GB 显存上做 QLoRA 微调时，环境隔离（虚拟环境）比在全局环境直接装包更稳妥？提示：想想不同项目对 PyTorch 版本或 CUDA 版本的依赖差异。

## 块 7

### 2.4 操作系统与实训环境该怎么选

你已经熟悉 PyTorch 和 Transformer，接下来要在 8GB 显存上跑 QLoRA 微调。环境选型这件事，核心就一句话：**让日常练习环境和最终跑 GPU 训练的环境尽量一致**，这样能少踩很多坑。

**日常写 Python、练命令行（Windows 用户）**

推荐启用 **WSL2 + Ubuntu LTS**（如 Ubuntu 22.04/24.04 LTS）。它本质是在 Windows 里跑一个接近真实生产的 Linux 环境，命令、路径、包管理方式都和后续的服务器一致，比在 Windows 原生 CMD 里练命令更贴近实战。安装只需管理员 PowerShell 执行 `wsl --install` 即可。

**日常写 Python（macOS / Linux 用户）**

直接用本机终端就行，macOS 和 Linux 本身就是类 Unix 环境，和服务器行为一致，不需要额外折腾。

**LoRA / QLoRA 微调、vLLM 部署等 GPU 实训**

应使用**装有 Ubuntu LTS 的 NVIDIA GPU 云服务器，或本地实体 Linux（Ubuntu LTS）机器**。这类任务依赖 NVIDIA 驱动、CUDA 与显卡直通，Ubuntu LTS 对深度学习生态的支持最成熟、文档最全。你手头的 RTX 4060 8GB 属于本地实体 GPU，如果后续要跑 QLoRA 微调，优先考虑装 Ubuntu LTS 双系统或直接用云服务器，而不是在虚拟机里折腾。

> **⚠️ 不推荐的做法**：不要把 **"CentOS + VirtualBox 虚拟机"当作最佳方案**。CentOS Linux 8 已停止维护（EOL），CentOS Stream 8 也已于 2024 年 5 月停止维护，生态逐渐落后；而 VirtualBox 这类桌面虚拟机**默认无法直通 NVIDIA GPU**，跑不了真正的 GPU 训练，只适合做纯 CPU 的隔离小实验。命令练习用 WSL2/Ubuntu LTS，GPU 实训用云上或实体的 Ubuntu LTS，才是稳妥路线。

**与当前学习目标的关系**

你的目标是 QLoRA 微调，这属于 GPU 实训场景。按本块建议，你应该把环境锚定在 Ubuntu LTS 上——无论是云服务器还是本地实体机。日常命令练习可以用 WSL2 保持手感，但真正跑微调时，确保你的 GPU 环境是 Ubuntu LTS + NVIDIA 驱动 + CUDA 可用，而不是在 VirtualBox 里碰运气。

**思考题**：为什么说 VirtualBox 虚拟机"默认无法直通 NVIDIA GPU"？如果你只有一台 Windows 笔记本带 8GB 显卡，你会怎么规划日常练习和 GPU 实训的环境？

## 块 9

### 3.1 什么时候才需要镜像源

`pip` 是 Python 的包管理工具，用来安装第三方库（比如 `numpy`、`pandas`）。默认情况下，`pip` 从官方 PyPI 服务器（`pypi.org`）拉取包——这是**最权威、最完整、最应保留的默认源**。

结合你后续要做的 QLoRA 微调，`pip` 会频繁安装 `transformers`、`peft`、`bitsandbytes` 这类依赖。如果网络环境访问官方源明显变慢或经常超时，才考虑临时切到国内镜像。**镜像只是"网络不好时的临时加速手段"，不是必须永久替换的默认设置**——官方源始终是首选。

### 3.2 首选做法：临时指定镜像源（推荐）

如果只是某次安装慢，最干净的做法是**只对这一次安装临时指定镜像**，不改动任何全局配置：

```bash
pip install numpy -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 5.1 为什么用 Conda

前面提到，虚拟环境可以为每个项目创建独立的 Python 空间。**Conda** 是目前最主流的虚拟环境管理工具，它不仅能创建虚拟环境，还能管理不同版本的 Python 解释器本身。对于后续学习深度学习（需要 PyTorch、CUDA 等复杂依赖），conda 几乎是必备工具。

对你正在准备的 QLoRA 微调来说，这一点尤其关键：PyTorch 版本、CUDA 运行时、transformers 和 peft 等库的版本组合，往往因项目而异。Conda 让你能在不同项目间切换互不干扰的依赖集合，而不是在全局环境里反复装卸包。

### 5.2 安装 Conda：Anaconda vs Miniconda

有两个选择：

| 选项 | 特点 | 推荐人群 |
|------|------|----------|
| **Anaconda** | 体积大（约 500MB+），预装了大量数据科学库（numpy、pandas、jupyter 等） | 做数据分析、不想手动装包的用户 |
| **Miniconda** | 体积小（约 50MB），只包含 conda 和基础 Python，按需安装 | 希望环境干净、做项目开发的用户 |

**本文推荐 Miniconda**，因为环境更干净，后续需要用什么包装什么包。考虑到你之后要为 QLoRA 微调单独建环境、按需安装 PyTorch 和 HuggingFace 生态库，Miniconda 的按需安装方式正好匹配——不装用不到的库，环境更可控，排查依赖冲突时也更省事。

**安装步骤：**

1. 访问 https://docs.conda.io/en/latest/miniconda.html。
2. 下载对应系统的安装包（Windows 选 `.exe`，macOS 选 `.pkg` 或 `.sh`，Linux 选 `.sh`）。
3. 运行安装程序：
   - **Windows**：一路下一步，**保持默认、不要勾选 "Add Miniconda3 to my PATH environment variable"**（该选项被安装器标为"不推荐"）。把 Miniconda 直接塞进系统 PATH 容易和系统已有的 Python / 其他工具冲突，导致 `python`、`pip` 指向不明。日常改用开始菜单里的 **"Anaconda Prompt (Miniconda3)"** 来使用 conda 即可。
   - **macOS/Linux**：运行 `.sh` 文件后，按提示输入 `yes` 同意协议、选择安装路径，并在最后一步选择 `yes` 让安装器执行 **`conda init`**（完成 shell 初始化）。这样每次打开终端时 conda 会通过初始化脚本正确接管，而不是靠把目录硬加进 PATH。

4. **验证安装**：打开一个**新的**终端（Windows 用 **"Anaconda Prompt (Miniconda3)"**；macOS/Linux 关闭并重开终端使 `conda init` 生效），输入：


如果显示类似 `conda 24.x.x`，说明安装成功。

## 第八章：常见问题排查

环境搭建阶段最容易消耗耐心的不是安装本身，而是装完之后各种“命令找不到”“版本不对”的报错。下面这张排查表覆盖了从 Python 安装到 conda 环境激活的几类高频问题，建议你按“现象 → 原因 → 解决”的顺序对照处理。

| 问题现象 | 可能原因 | 解决方案 |
|----------|----------|----------|
| 输入 `python` 提示"不是内部或外部命令" | 安装时未勾选 "Add to PATH" | 重新运行 Python 安装程序，选择 "Modify"，勾选 "Add Python to environment variables" |
| `pip install` 速度极慢或超时 | 网络受限，访问官方 PyPI 慢 | 临时加 `-i` 指定国内镜像，例如：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple <包名>`；长期受限再考虑设为默认源 |
| `conda` 命令找不到 | 未安装 Anaconda/Miniconda，或安装时未将 conda 加入 PATH | 重新安装并勾选 Add to PATH，或手动将 conda 的 bin 目录添加到 PATH 环境变量 |
| VS Code 提示"未选择 Python 解释器" | 未配置解释器路径 | 按 `Ctrl + Shift + P` → `Python: Select Interpreter` 手动选择 |
| 激活 conda 环境后，`python` 版本不对 | 系统里存在多个 Python | 使用 `where python`（Windows）或 `which python`（Mac/Linux）查看路径，确保指向 conda 环境 |
| pip 安装后，Python 里 `import` 报错 | pip 装到了错误的环境 | 激活目标 conda 环境后，使用 `python -m pip install 包名` 安装 |

几个值得留意的点：

- **PATH 问题**是“命令找不到”类报错的最常见根源。`python` 本身装好了，但系统不知道去哪找它。解决方案里提到的 "Modify" 修复路径，本质是让安装器帮你把 Python 的可执行文件目录写进系统环境变量，一劳永逸。
- **`pip` 慢**的解法里，`-i` 参数是临时指定镜像源，只对当前这条命令生效；如果每次都要带，说明值得考虑把镜像设为默认。这个决策取决于你的网络环境是否长期受限。
- **多 Python 共存**是 conda 环境“版本不对”的典型场景。`where python` / `which python` 的作用是打印出当前 shell 实际解析到的 Python 路径，帮你确认激活环境后到底调用了哪个解释器。这一步排查思路对后续做 QLoRA 微调同样重要——你肯定不希望装好的 `bitsandbytes` 或 `transformers` 被另一个环境的 Python 意外调用。
- **`python -m pip install`** 比直接 `pip install` 更稳妥，因为它显式指定了“用当前这个 Python 解释器去执行 pip”，从根源上避免装错环境。

**思考题**：如果你在 RTX 4060 8GB 上做 QLoRA 微调，激活 conda 环境后 `import torch` 报错说 CUDA 不可用，你会用上面哪一行命令来定位问题？为什么？

**与当前学习目标的关系**：QLoRA 微调依赖一整套 Python 环境（PyTorch、transformers、peft、bitsandbytes 等），而这一章排查的正是这套环境能否被正确加载的底层问题。你已熟悉 PyTorch 和 Transformer，但环境层面的“解释器选错”“包装错环境”恰恰是微调前最容易踩的坑——先确保 `python`、`pip`、conda 环境三者指向一致，后续跑微调脚本时才能把精力放在模型和训练参数上，而不是被环境报错打断。

如果在排查过程中遇到表格里没覆盖的报错，或某个术语（比如 `conda init` 具体做了什么）解释不清，先记下来，之后提问时一起讨论。
