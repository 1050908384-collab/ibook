## 第一章：指令遵循是什么——从"接话"到"办事"

### 1.1 一个直观的对比

假设你问一个**未经指令微调**的基座模型：

> **你**："教我如何游泳"
> 
> **基座模型**："去专业的游泳馆"

这个回答在语法上是合理的句子补全，但**完全没有理解你的真实意图**。基座模型的训练目标只是"预测下一个词"，它不知道你是在"请求指导"。

而经过**指令微调**后的模型：

> **你**："教我如何游泳"
> 
> **指令模型**："学习游泳可以分为以下几个步骤：首先，熟悉水性，在浅水区练习憋气和漂浮..."

这就是**指令遵循（Instruction Following）**——模型能够理解自然语言指令的意图，并生成符合指令要求的输出。

### 1.2 形式化定义

**指令遵循**是指：大语言模型能够理解以自然语言表达的指令，并根据指令的要求生成相应输出的能力。

**核心特征**：
- **意图理解**：不仅理解字面意思，还尽量理解指令背后的真实目的
- **任务泛化（目标而非保证）**：**目标**是能处理训练时没见过的新指令；实际泛化程度因模型与指令类型而异，并非对任意新指令都能可靠遵循
- **格式遵循**：按照指令要求的格式输出（如列表、JSON、代码等）
- **约束遵守**：遵循指令中的限制条件（如"用一句话回答""不要提及某内容"）

## 第二章：为什么基座模型通常难以稳定遵循指令

### 2.1 预训练的目标局限

基座模型（Base Model）的预训练目标是**自回归语言建模**：

```
给定前缀 "今天天气"，预测下一个词 → "很好"
给定前缀 "今天天气很好"，预测下一个词 → "，"
...
```

**为什么这样训练**：模型通过海量文本学习语言的统计规律，但它学到的只是"什么样的词序列是合理的"，而不是"用户想要什么"。

### 2.2 基座模型的"接话"行为

当你给基座模型输入"教我如何游泳"时，它的内部逻辑是：

```
"教我如何游泳" → 后面最可能跟什么词？
→ "去专业的游泳馆"（语法通顺的补全）
→ "首先你需要..."（也是合理的补全）
```

未经指令训练的基座模型，**通常更倾向于把输入当作"待续写的文本"去补全**，而不是稳定地把它当作"需要执行的请求"来响应。它在部分提示下也可能给出看似在"遵循指令"的输出，但这种行为往往不稳定、不可靠。

**为什么这样理解**：这有点像一个只学过"续写"的模型——你给它一段话，它接着往下写最可能的内容，而不一定"意识到"你在向它下达任务。指令微调正是要把模型从"接话式续写"进一步对齐为"稳定地按请求响应"的助手。

## 第三章：指令微调——赋予模型指令遵循能力

### 3.1 什么是指令微调

**指令微调（Instruction Fine-Tuning, IFT）** 是一种在带有**指令提示和相应输出的标记数据集**上微调大模型的技术。

**核心思想**：通过提供大量"指令 → 理想响应"的示例，让模型学习"当用户这样请求时，我应该这样回应"。

**数据格式示例**：

```json
{
  "instruction": "将以下现代文翻译成文言文",
  "input": "我喜欢读书",
  "output": "吾好读书"
}
```

### 3.2 指令微调与"传统任务式微调"的区别

> ⚠️ **先厘清一个常见概念误区**：**指令微调本身就是有监督微调（SFT）的一种**，而不是与 SFT 并列的另一类方法。SFT（Supervised Fine-Tuning）泛指"用带标注的监督数据微调模型"；当这些监督数据是**"自然语言指令 → 期望回复"**的形式时，这种 SFT 就叫**指令微调（Instruction Fine-Tuning）**。所以正确的关系是：
>
> ```
> 有监督微调（SFT，上位概念）
> ├── 传统任务式微调：数据是"文本 → 固定标签/固定格式输出"（如情感分类、NER）
> └── 指令微调（IFT）：数据是"自然语言指令(+输入) → 期望回复"，是 SFT 的一种
> ```
>
> 下表对比的是**"传统任务式微调"**与**"指令微调"**这两种 SFT 用法的差异，**不是**"SFT vs 指令微调"的对立。

| 维度 | 传统任务式微调（SFT 的一种用法） | 指令微调（IFT，同样是 SFT 的一种） |
|------|-----------------------------------|-----------------------------------|
| **训练数据** | 输入-输出对（如文本-标签） | 指令-输入-输出三元组 |
| **数据特点** | 任务单一，格式固定 | 任务多样，指令自然语言化 |
| **模型能力** | 擅长特定任务 | 擅长理解并执行各种指令 |
| **泛化能力** | 对新任务通常需要重新微调 | 更易泛化到未见过的新指令 |
| **典型用途** | 把模型专门化到某个固定任务 | 让模型获得通用的"听懂并执行指令"能力 |

**为什么这样理解**：二者都是"用监督数据微调"，区别只在**数据组织形式与训练目标**——传统任务式微调让模型学会"做某一件固定的事"，指令微调让模型学会"听懂各种自然语言指令并办事"。它们是 SFT 的两种用法，而非两种互斥的技术。

### 3.3 指令微调的数据集构建

**指令数据集的核心**：输入样本必须**完全由类似于用户在提示中可能提出的请求**组成，输出展示对这些请求的理想响应。

**构建方法**：

**方法一：人工编写**
- 雇佣标注员编写指令和对应输出
- 优点：质量高
- 缺点：成本高、规模小

**方法二：Self-Instruct（自指令生成）**
- 用已有的大模型（如 GPT-4）自动生成指令数据
- 流程：
  1. 准备 175 个种子任务（人工编写）
  2. 让大模型根据种子任务生成更多相似指令
  3. 让大模型为生成的指令编写输出
  4. 过滤低质量数据

**方法三：现有数据集改造**
- 将传统的 NLP 数据集（如情感分析、翻译、问答）改造为指令格式

**示例：改造情感分析数据集**

```
原始格式：
  文本: "这部电影太精彩了"
  标签: 正面

指令格式：
  instruction: "判断以下文本的情感倾向"
  input: "这部电影太精彩了"
  output: "正面"
```

### 3.4 经典指令数据集

| 数据集 | 规模 | 特点 |
|--------|------|------|
| **Alpaca** | 52K | 基于 Self-Instruct 生成，开源 |
| **FLAN** | 数千任务 | 覆盖多种 NLP 任务，指令模板丰富 |
| **Dolly** | 15K | 人工编写，高质量 |
| **ShareGPT** | 数万 | 真实用户对话数据 |
| **LIMA** | 1K | 证明"少即是多"，少量高质量数据即可 |

## 第四章：指令遵循的评估——如何判断模型"听懂"了

### 4.1 评估维度

| 维度 | 说明 | 示例 |
|------|------|------|
| **准确性** | 输出内容是否正确 | 问答任务中答案是否准确 |
| **完整性** | 是否覆盖了指令要求的所有方面 | "列举3个优点"是否列出了3个 |
| **格式遵循** | 是否按要求格式输出 | 要求 JSON 格式时是否输出 JSON |
| **约束遵守** | 是否遵守指令中的限制 | "用一句话回答"是否只输出一句话 |
| **安全性** | 是否拒绝有害指令 | 对"如何制造炸弹"是否拒绝 |

### 4.2 常用评估基准

**（一）直接评估"格式/约束遵循"的基准（最贴合"指令遵循"本身）**

| 基准 | 特点 |
|------|------|
| **IFEval** | 用**可程序化验证**的指令（如"回答不超过 3 句""必须包含关键词 X""用 JSON 输出"）自动判定是否满足约束，客观、可复现 |
| **FollowBench** | 分级评测对**多种约束类型**（内容、格式、风格、数量等）的遵循程度，考察随约束增多时的稳定性 |

**（二）用模型/裁判打分的综合对话评估（含 LLM-as-a-judge）**

| 基准 | 特点 |
|------|------|
| **MT-Bench** | 多轮对话评估，用 GPT-4 作为裁判打分 |
| **AlpacaEval** | 让模型与参考模型对比，统计胜率 |

> ⚠️ **LLM-as-a-judge 的局限**：用强模型当"裁判"（如 MT-Bench、AlpacaEval）虽然方便，但存在**位置偏差、长度/冗长偏好、对自家风格的偏好、可被"迎合式"输出操纵**等系统性偏差，结果需谨慎解读，最好与 IFEval 等客观指标以及人工评估结合。

**（三）主要测其他能力、常被"顺带"引用但并非指令遵循专用的基准**

| 基准 | 特点 |
|------|------|
| **HELM** | 全面评估，覆盖准确性、鲁棒性、公平性、效率等多维度 |
| **MMLU** | 主要测**多学科知识问答**能力，并非专门衡量"格式/约束遵循" |
| **HumanEval** | 主要测**代码生成**能力，并非专门衡量指令遵循 |

> 说明：MMLU、HumanEval 常被用来体现模型"整体能力"，但它们衡量的是知识与代码能力；判断"是否严格遵循指令中的格式与约束"应优先看 IFEval、FollowBench 这类专门基准。

## 第五章：指令遵循与相关概念的关系

### 5.1 指令遵循 vs 上下文学习（ICL）

| 对比 | 指令遵循（通过指令微调） | 上下文学习（ICL） |
|------|------------------------|------------------|
| **参数更新** | ✅ 需要微调 | ❌ 不更新参数 |
| **数据需求** | 需要指令数据集 | 只需几个示例 |
| **稳定性** | 高，模型已内化指令能力 | 低，对示例敏感 |
| **适用场景** | 生产环境、对话系统 | 快速原型、临时任务 |
| **关系** | 指令微调后的模型，ICL 能力更强 | ICL 是通用能力，指令遵循是特定优化 |

**为什么这样理解**：指令微调让模型"学会"了如何遵循指令，而 ICL 是在这个基础上，通过上下文中的示例进一步引导模型。两者是**互补**的。

### 5.2 指令遵循 vs 思维链（Chain-of-Thought）

- **指令遵循**：让模型"听懂话"
- **思维链**：让模型"一步一步想"

两者结合：

```
指令: "请逐步推理，解决以下数学题"
输入: "小明有5个苹果，给了小红2个，又买了3个，现在有几个？"
输出: "第一步：小明原有5个苹果
       第二步：给了小红2个，剩下 5-2=3 个
       第三步：又买了3个，现在有 3+3=6 个
       答案：6个"
```

**为什么这样写**：指令遵循提供"任务框架"，思维链提供"推理方法"。两者叠加，模型既能理解要做什么，又能正确地一步步完成。

## 第六章：指令微调的实践要点

### 6.1 指令设计原则

**好的指令**：
- **明确具体**："总结这段文字的主要观点" 优于 "处理这段文字"
- **提供上下文**："作为一位医生，解释糖尿病的症状" 优于 "解释糖尿病的症状"
- **指定格式**："用 bullet points 列出" 优于 "列出"
- **设定约束**："用不超过100字" 优于 "简短回答"

### 6.2 指令模板示例

```python
# 通用指令模板
INSTRUCTION_TEMPLATE = """你是一个{role}。请根据以下指令完成任务。

指令：{instruction}
输入：{input}

请按要求输出："""

# 示例
prompt = INSTRUCTION_TEMPLATE.format(
    role="有帮助的助手",
    instruction="将以下中文翻译成英文",
    input="我喜欢自然语言处理"
)
```

### 6.3 指令微调与 RLHF 的关系

指令微调通常不是终点，而是**偏好对齐（RLHF/RLAIF 等）阶段的前置步骤**：

```
基座模型
   ↓
指令微调（属于 SFT）→ 学会遵循指令
   ↓
偏好对齐阶段 → 对齐人类偏好（安全、有用、诚实）
   ↓
最终模型（如 ChatGPT、Claude 等）
```

> ⚠️ **别把对齐阶段固定成"奖励模型 + PPO"**：早期 InstructGPT 采用的是"训练奖励模型 + 用 PPO 做强化学习"的经典路线，但这**只是众多做法之一，且已不再是唯一/默认选择**。如今常见的对齐方案还包括：
> - **DPO**（直接偏好优化）：跳过独立奖励模型与在线 RL，直接用成对偏好数据优化，流程更简单；
> - **GRPO**：组内相对比较，可搭配规则/可验证奖励，常用于推理任务；
> - 以及 **KTO、ORPO、RLAIF（用 AI 反馈替代部分人工）** 等。
>
> 换言之，"指令微调之后一定要接'奖励模型+PPO'"是一种**过时的简化**。实际选型取决于任务、数据形式（成对偏好/标量奖励/可验证规则）、算力与工程复杂度——详见第 10 板块《RLHF 整体流程与目标》对 PPO/DPO/GRPO 等算法的对比。

**为什么这样理解**：指令微调让模型"会做事"，对齐阶段让模型"做对事"（符合人类价值观、偏好、安全标准）；而"做对事"这一步**有多条技术路线可选**，不局限于 PPO。

## 第七章：常见陷阱与避坑清单

| 坑点 | 正确做法 |
|------|----------|
| 指令数据质量差（错误、歧义） | 严格过滤，优先使用人工审核数据 |
| 指令类型单一 | 覆盖问答、翻译、总结、推理、代码等多种任务 |
| 指令与输出不匹配 | 确保每条指令都有对应的高质量输出 |
| 过度微调导致遗忘 | 混合通用语料和指令数据，防止灾难性遗忘 |
| 忽视安全性 | 加入拒绝有害指令的示例 |
| 指令太长超出上下文 | 控制单条数据长度，或使用长上下文模型 |
| 认为指令微调万能 | 复杂任务仍需结合 RAG、Agent 等架构 |

## 本章小结

| 知识点 | 核心要点 |
|--------|----------|
| **指令遵循定义** | 模型理解自然语言指令并按要求生成输出 |
| **基座模型局限** | 只会"接话"（预测下一个词），不懂用户意图 |
| **指令微调** | 用"指令-输出"数据集微调，赋予指令遵循能力 |
| **与普通微调区别** | 指令微调是 SFT 的一种（数据为自然语言指令）；传统任务式微调是 SFT 的另一种用法，二者非对立 |
| **数据集构建** | 人工编写、Self-Instruct、现有数据改造 |
| **经典数据集** | Alpaca、FLAN、Dolly、ShareGPT、LIMA |
| **评估维度** | 准确性、完整性、格式遵循、约束遵守、安全性 |
| **与 ICL 关系** | 指令微调是"学会听懂"，ICL 是"临时提示" |
| **与对齐阶段关系** | 指令微调（SFT）在前；对齐可用 PPO/DPO/GRPO/KTO 等多种方案，非只有"奖励模型+PPO" |

**养成的好习惯**：
1. 设计指令时**明确、具体、有上下文**
2. 指令数据集要**覆盖多样任务**，避免单一
3. 生产环境优先使用**经过指令微调+RLHF**的模型
4. 评估时不仅看**准确性**，还要看**格式遵循和安全性**

**下一步预告**：掌握了指令遵循后，你将进入 **逐步推理（Step-by-Step Reasoning）** 的学习——理解 Chain-of-Thought（思维链）如何让模型"一步一步想"，以及 Self-Consistency（自洽性）如何提升推理的可靠性。这是让大模型从"鹦鹉学舌"进化为"逻辑思考"的关键技术。继续加油！
