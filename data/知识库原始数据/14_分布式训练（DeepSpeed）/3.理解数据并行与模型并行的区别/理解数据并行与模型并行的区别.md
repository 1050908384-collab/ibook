## 第一章：为什么需要分布式训练——从单卡瓶颈说起

### 1.1 单卡训练的两大瓶颈

训练大语言模型时，单张 GPU 会遇到两个维度的瓶颈：

| 瓶颈维度 | 问题描述 | 触发条件 |
|---------|---------|---------|
| **数据维度** | 单个 batch 的数据量太大，单卡显存放不下激活值 | 模型不大，但 batch size 大或序列长 |
| **模型维度** | 模型参数量太大，单卡显存放不下模型权重 | 模型参数量超过单卡显存容量 |

**为什么这样写**：如果模型又小、batch 又少，一张卡跑就够了，不需要任何并行。只有当上述两个维度中至少一个触碰到天花板时，才需要引入分布式训练策略。

### 1.2 两种解决思路

面对这两个瓶颈，业界发展出了两种截然不同的解决思路：

```
┌─────────────────────────────────────────────────────────────┐
│  数据维度瓶颈 → 数据并行（DP）                                │
│  核心思想：模型不变，把数据切开，每张卡处理一部分数据            │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  模型维度瓶颈 → 模型并行（MP）                                │
│  核心思想：数据不变，把模型切开，每张卡只存一部分参数            │
└─────────────────────────────────────────────────────────────┘
```

**为什么这样写**：DP 和 MP 不是互斥的，而是解决不同瓶颈的两种工具。实践中常常将它们组合使用，形成混合并行策略。

## 第二章：数据并行（DP）——复制模型，分摊数据（①）

### 2.1 核心原理：复制模型，分摊数据

数据并行（Data Parallelism, DP）是最简单、最广泛应用的并行策略。

**工作流程**：
1. **模型复制**：每张 GPU 都保存一份完整的模型副本
2. **数据切分**：将全局 batch 数据划分为多个子批次（micro-batch），分发到不同 GPU
3. **独立计算**：每张卡独立进行前向传播和反向传播，计算本地梯度
4. **梯度同步**：通过 AllReduce 操作将所有卡的梯度聚合（求平均）
5. **统一更新**：每张卡用相同的平均梯度更新自己的模型副本

```
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ 数据片1  │  │ 数据片2  │  │ 数据片3  │  │ 数据片4  │
└────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘
     ↓            ↓            ↓            ↓
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ 完整模型 │  │ 完整模型 │  │ 完整模型 │  │ 完整模型 │
│  GPU 0  │  │  GPU 1  │  │  GPU 2  │  │  GPU 3  │
└────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘
     └────────────┴────────────┴────────────┘
                    ↓
              AllReduce 梯度同步
                    ↓
     ┌────────────┬────────────┬────────────┐
     ↓            ↓            ↓            ↓
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ 更新后模型│  │ 更新后模型│  │ 更新后模型│  │ 更新后模型│
└─────────┘  └─────────┘  └─────────┘  └─────────┘
```

**为什么这样写**：DP 的数学基础非常简洁——每张卡计算的梯度是对应数据子集的梯度，AllReduce 求平均后在数学上对应全局 batch 的梯度。因此在忽略实现细节的理想情况下，DP 与"用同样全局 batch 的单卡训练"近似等价。需要注意，这种等价是有前提的：涉及跨样本统计的算子（如未做同步的 BatchNorm）、随机性（dropout 种子）、以及浮点累加顺序不同等因素，都可能让多卡结果与单卡不完全逐位一致。

### 2.2 通信开销分析（①）

DP 的通信发生在**每轮训练的反向传播结束后**，通信量为：

$$\text{通信量} = 2 \times M \times \text{dtype}$$

其中 $M$ 是模型参数量，`dtype` 是数据类型（FP16 为 2 字节）。系数 2 是因为 AllReduce 的内部实现等价于 Reduce-Scatter + All-Gather 两步。

**为什么这样写**：DP 的通信频率很低（每步一次），且通信量只与模型大小有关，与 batch size、序列长度无关。这是 DP 效率高的根本原因。

### 2.3 PyTorch DDP 代码实现（①）

```python
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

# 初始化进程组
dist.init_process_group(backend='nccl')

# 将模型封装为 DDP
model = MyModel().cuda()
ddp_model = DDP(model, device_ids=[torch.cuda.current_device()])

# 训练步骤
for data, labels in dataloader:
    data, labels = data.cuda(), labels.cuda()
    outputs = ddp_model(data)
    loss = loss_fn(outputs, labels)
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
```

**为什么这样写**：
- `backend='nccl'`：NVIDIA 提供的 GPU 间通信库，效率最高
- `DDP` 封装在反向传播时**自动触发梯度同步**，无需手动调用 AllReduce
- `DistributedSampler` 确保数据不重不漏地划分到各卡

### 2.4 DP 的优缺点

| 优点 | 缺点 |
|------|------|
| 实现简单，框架原生支持 | 单卡必须能放下完整模型 |
| 通信频率低（每步一次） | 模型过大时无法使用 |
| 通信量与 batch size 无关 | 激活值随 batch 增大而增加 |
| 线性加速比接近理想值 | 多机场景下受网络带宽限制 |

**适用场景**：模型能放进单卡显存，但数据量巨大（如 7B 模型在 80GB 显存上训练）。

## 第三章：模型并行（MP）——拆分模型，协同计算

当模型本身过大，单卡无法容纳时，必须将**模型切分**到多张卡上。模型并行主要分为两种：**张量并行（TP）**和**流水线并行（PP）**。

### 3.1 张量并行（Tensor Parallelism, TP）（①）

#### 3.1.1 核心思想：层内切分

张量并行在**单个层内部**拆分权重矩阵，利用分块矩阵乘法进行计算。

**以 Transformer MLP 层为例**：

MLP 包含两个矩阵乘法：
- 第一个线性层：$Y = X \times A$，其中 $A$ 形状为 $h \times 4h$
- 第二个线性层：$Z = Y \times B$，其中 $B$ 形状为 $4h \times h$

**切分策略**：
- 第一个矩阵 $A$ **按列切分**：$A = [A_1, A_2]$，每张卡计算 $X \times A_1$ 和 $X \times A_2$
- 经过激活函数后，第二个矩阵 $B$ **按行切分**：$B = \begin{bmatrix} B_1 \\ B_2 \end{bmatrix}$，每张卡计算后通过 AllReduce 汇总

```
GPU 0                    GPU 1
┌─────────┐             ┌─────────┐
│  X×A₁   │             │  X×A₂   │
│  GeLU   │             │  GeLU   │
│ Y₁×B₁   │             │ Y₂×B₂   │
└────┬────┘             └────┬────┘
     └──────────┬────────────┘
                ↓
           AllReduce
                ↓
             Z = Z₁ + Z₂
```

**为什么这样写**：如果第一个矩阵按行切、第二个按列切，第一个矩阵的结果在激活前就需要 AllReduce，既没节省空间又增加了通信。按"列切 + 行切"的组合，中间结果无需同步，只在最后做一次 AllReduce。

#### 3.1.2 Attention 层的 TP 实现（①）

多头注意力（MHA）天然适合张量并行——直接按 **head 维度切分**：

```
原始：8 heads          TP=2 切分后
┌─────────────────┐    ┌─────────┐  ┌─────────┐
│ Q,K,V: 8 heads  │ →  │ 4 heads │  │ 4 heads │
│      GPU 0      │    │  GPU 0  │  │  GPU 1  │
└─────────────────┘    └─────────┘  └─────────┘
```

**约束**：`num_heads` 必须能被 `tp_size` 整除。例如 8 heads 可以切分到 2 卡或 4 卡，但不能切到 3 卡。

#### 3.1.3 TP 的通信开销（①）

TP 每层都需要 AllReduce 同步，通信开销为：

$$\text{通信量} \approx 2 \times b \times s \times h \times L$$

其中 $b$=batch size，$s$=序列长度，$h$=hidden size，$L$=层数。

**为什么这样写**：TP 的通信量与序列长度和 batch size 成正比，且**每层都要通信**。因此 TP 对卡间带宽要求极高，**通常只在单机多卡（如单机 8 卡）范围内使用**（依赖 NVLink 等高速互联，不同代际的 NVLink 带宽差异较大，从每卡数百 GB/s 到接近 TB/s 量级不等，以具体硬件规格为准），跨机时即便有 InfiniBand 也往往难以承受。

### 3.2 流水线并行（Pipeline Parallelism, PP）（①）

#### 3.2.1 核心思想：层间切分

流水线并行按**网络层数**将模型切分为多个阶段（stage），每张卡负责一部分层的前向和反向计算。

```
GPU 0 (Layers 0-9)    GPU 1 (Layers 10-19)   GPU 2 (Layers 20-29)   GPU 3 (Layers 30-39)
┌─────────┐           ┌─────────┐            ┌─────────┐            ┌─────────┐
│ 输入    │──────────→│ 中间    │───────────→│ 中间    │───────────→│ 输出    │
│ 激活值  │           │ 激活值  │            │ 激活值  │            │ 损失    │
└─────────┘           └─────────┘            └─────────┘            └─────────┘
     ↑                     ↑                      ↑                      │
     └─────────────────────┴──────────────────────┘←─────────────────────┘
                              反向传播
```

**为什么这样写**：PP 的通信只发生在相邻 stage 之间，传递的是**激活值**（而非梯度），通信量为 $b \times s \times h$，远小于 TP 的频繁 AllReduce。

#### 3.2.2 气泡问题（Bubble）（①）

PP 最大的问题是**气泡（Bubble）**——由于前向传播需要逐层传递，后续 GPU 必须等待前序 GPU 完成，导致空闲。

```
时间 →
Device 1: [F1][F2][F3][F4]      [B1][B2][B3][B4]
Device 2:      [F1][F2][F3][F4]      [B1][B2][B3][B4]
Device 3:           [F1][F2][F3][F4]      [B1][B2][B3][B4]
Device 4:                [F1][F2][F3][F4]      [B1][B2][B3][B4]
              ↑↑↑↑↑↑↑ 气泡（空闲等待） ↑↑↑↑↑↑↑
```

**优化方案——1F1B（One Forward One Backward）**（①）：
将全局 batch 拆分为多个 micro-batch，采用"来一个处理一个"的策略，让反向传播尽早开始，减少显存占用。

**进一步优化——Interleaved 1F1B（Virtual Pipeline）**（①）：
将每个 stage 再细分为多个虚拟 stage，进一步降低气泡率。例如 4 个 GPU 原本 4 个 stage，虚拟化后可模拟 8 个 stage，气泡率降低一半。

## 第四章：数据并行 vs 模型并行——核心区别对比

### 4.1 全面对比表

| 对比维度 | 数据并行（DP） | 张量并行（TP） | 流水线并行（PP） |
|---------|-------------|-------------|---------------|
| **切分对象** | 数据 batch | 层内权重矩阵 | 层间网络结构 |
| **单卡模型** | 完整副本 | 部分参数 | 部分层 |
| **单卡数据** | 子集 | 完整 batch | 完整 batch |
| **通信内容** | 梯度 | 激活值/中间结果 | 激活值 |
| **通信频率** | 每步一次 | 每层一次 | 阶段间传递 |
| **通信量** | $2 \times M \times \text{dtype}$ | $O(b \times s \times h \times L)$ | $O(b \times s \times h \times pp)$ |
| **卡间带宽要求** | 中 | **极高**（需 NVLink） | 低 |
| **跨机可行性** | ✅ 可行 | ❌ 不推荐 | ✅ 可行 |
| **实现复杂度** | 低 | 高 | 中 |
| **适用模型规模** | 中小模型（可放进单卡） | 大模型（层内参数过大） | 超大模型（层数过多） |

### 4.2 选型决策树

```
模型能否放进单卡显存？
├── 能 → 数据并行（DP）即可，效率最高
│        └── batch 太大？→ DP + 梯度累积
└── 不能 → 进入下一步

单层参数是否过大（如 MLP 的 h→4h 矩阵放不下了）？
├── 是 → 引入张量并行（TP），层内切分
└── 否 → 进入下一步

模型层数是否过多（如 80+ 层）？
├── 是 → 引入流水线并行（PP），层间切分
└── 否 → 检查是否是激活值/序列长度过大

最终方案：
├── 单机 8 卡：DP + TP（如 Megatron-LM）
├── 多机集群：DP + PP + TP（如 GPT-3 训练配置）
└── 超大模型：DP + PP + TP + ZeRO-3（如 LLaMA-70B）
```

### 4.3 为什么 DP 效率最高？（①）

DP 被称为"所有并行中效率最高"的策略，原因在于：

1. **通信频率最低**：每步训练只通信一次，TP 每层都要通信
2. **通信量固定**：只与模型大小有关，与 batch size、序列长度无关
3. **计算密度高**：每张卡执行完整的前向+反向，在数据供给充足、通信可与计算重叠时 GPU 利用率可以很高

**为什么这样写**：PP 有气泡等待，TP 有频繁同步，DP 在这几种基础策略里最容易让 GPU 保持较高的计算利用率。因此**一个常用经验是：只要模型能放进单卡，就优先考虑 DP，不要过早引入 TP/PP 增加复杂度**（当然，若数据供给或网络成为瓶颈，DP 的扩展效率同样会下降）。

## 第五章：混合并行策略——DP+TP+PP 的组合艺术（①②）

### 5.1 为什么需要混合并行？

单一并行策略往往无法兼顾所有需求。以训练一个 175B 参数的 GPT 模型为例：

- 模型太大，单卡放不下 → 需要 MP（TP + PP）
- 数据量巨大，需要加速训练 → 需要 DP
- 要在合理时间内完成训练 → 需要同时使用 DP + TP + PP

**典型配置（以 GPT-3 175B 为例）**：
- 96 层 Transformer，hidden size 12288（这两项是 GPT-3 175B 的公开结构参数）
- 训练时综合使用 TP（单机内）、PP（跨机）、DP（跨节点）等多种并行，并动用上千张 A100 级别的 GPU
- 具体的并行度组合（如 TP/PP/DP 各多少路、共用多少张卡）在不同资料里的描述并不一致，下面给出的是一种**便于理解的示例拆分，并非唯一或官方定论**：8 路 TP + 8 路 PP + 16 路 DP（合计约 1024 张 GPU）

### 5.2 混合并行的通信组划分（①）

在混合并行中，GPU 被组织为多个**通信组**：

```
┌─────────────────────────────────────────────────────────────┐
│  节点 0 (8×A100, NVLink)                                    │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐          │
│  │ GPU 0   │ │ GPU 1   │ │ GPU 2   │ │ GPU 3   │  TP 组 0  │
│  │ GPU 4   │ │ GPU 5   │ │ GPU 6   │ │ GPU 7   │  (8 卡)   │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘          │
│                    ↑ AllReduce (TP)                         │
└─────────────────────────────────────────────────────────────┘
                           ↓ 传递激活值 (PP)
┌─────────────────────────────────────────────────────────────┐
│  节点 1 (8×A100, NVLink)                                    │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐          │
│  │ GPU 8   │ │ GPU 9   │ │ GPU 10  │ │ GPU 11  │  TP 组 1  │
│  │ GPU 12  │ │ GPU 13  │ │ GPU 14  │ │ GPU 15  │  (8 卡)   │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘          │
└─────────────────────────────────────────────────────────────┘
                           ↓ AllReduce (DP)
                    跨节点梯度同步
```

**为什么这样写**：
- **TP 组**：单机内 8 卡，通过 NVLink 高频 AllReduce
- **PP 组**：跨机的对应 TP 组之间传递激活值
- **DP 组**：相同 stage 的 GPU 之间同步梯度

### 5.3 DeepSpeed 中的混合并行配置（②）

```json
{
  "train_batch_size": 64,
  "train_micro_batch_size_per_gpu": 1,
  "gradient_accumulation_steps": 8,
  "model_parallel_size": 8,
  "pipeline_parallel_size": 4,
  "zero_optimization": {
    "stage": 1
  }
}
```

**为什么这样写**：
- `model_parallel_size`: 8 → 张量并行 8 路
- `pipeline_parallel_size`: 4 → 流水线并行 4 路
- 剩余并行度自动分配给数据并行

## 第六章：电脑配置批注

本章节涉及分布式训练的理论与实践，本地和云端场景均需考虑。

### 6.1 本地环境配置要求

| 项目 | 最低配置 | 推荐配置 |
|------|---------|---------|
| **GPU** | 2 张 NVIDIA GPU，显存 ≥16GB/卡 | 4~8 张 A100（40GB/80GB），NVLink 互联 |
| **CPU** | 8 核 | 16 核+ |
| **内存** | 32GB | 64GB+ |
| **磁盘** | 100GB SSD | 500GB+ NVMe SSD |
| **网络** | PCIe（单机多卡） | NVLink（单机内 TP）+ 10Gbps+ 以太网（多机） |
| **是否支持 CPU 运行** | ❌ 不支持（需 GPU） | — |

### 6.2 云端环境配置参考

| 场景 | 推荐实例 | 适用并行策略 |
|------|---------|-------------|
| 低成本 DP 实验 | AutoDL 2×RTX 3090 | 纯 DP |
| 标准 TP 实验 | AWS p3.8xlarge（4×V100） | DP + TP |
| 大规模混合并行 | AWS p4d.24xlarge（8×A100） | DP + TP + PP |
| 超大规模训练 | 多节点 A100 集群（64~1024 卡） | DP + TP + PP + ZeRO-3 |

### 6.3 不同并行策略的硬件要求

| 并行策略 | 最低 GPU 数量 | 卡间带宽要求 | 网络要求 |
|---------|-------------|-------------|---------|
| DP | 2 卡 | 低 | 普通以太网即可 |
| TP | 2 卡（需整除 head 数） | **极高**（强烈建议 NVLink/NVSwitch） | 优先单机；PCIe/跨节点可运行但通信易成瓶颈 |
| PP | 2 卡 | 中 | 跨机需 10Gbps+ |
| DP+TP | 4 卡（2×2） | 组内极高、组间低 | 单机优先 |
| DP+TP+PP | 8 卡+ | 组内极高、组间中 | 多机 InfiniBand |

## 第七章：常见问题与避坑清单

| 坑点 | 现象 | 解决方案 |
|------|------|---------|
| **TP head 数不整除** | 报错 `num_heads % tp_size != 0` | 确保 `num_heads` 能被 `tp_size` 整除，如 8 heads 可切 2/4/8 路 |
| **TP 跨机使用** | 训练速度骤降 | TP 强烈依赖高速互联，通常优先限制在单机 NVLink/NVSwitch 域内；跨机并非不能运行，但通信极易成为瓶颈，一般跨机改用 DP/PP，是否可行应通过基准测试确认 |
| **PP 气泡过大** | GPU 利用率低，大量时间空闲 | 增大 micro-batch 数量；使用 Interleaved 1F1B；调整 stage 负载均衡 |
| **DP 模型放不进单卡** | OOM 报错 | 传统"复制式"数据并行（每卡存完整模型）确实无法解决。**分片数据并行**能缓解，但要看分片到哪一级：ZeRO-2 只分片"梯度 + 优化器状态"、**每卡仍保留完整参数**，因此只有当"参数放得下、但完整训练状态放不下"时才管用；若**权重本身就放不进单卡**，需要用 **ZeRO-3 / FSDP 的 `FULL_SHARD`**（进一步分片模型参数）或 TP/PP。不要笼统地说"ZeRO-2/3、FSDP 都能分片参数" |
| **混合并行通信组冲突** | NCCL 报错、进程挂起 | 确保 TP/PP/DP 的通信组互不重叠，使用 `torch.distributed.new_group()` 明确划分 |
| **梯度同步不同步** | 多卡 loss 发散 | 检查是否所有进程都调用了 `backward()`；确认 AllReduce 已完成 |

## 本章小结

| 知识点 | 核心要点 |
|--------|----------|
| **DP 核心思想** | 复制模型，分摊数据，每步一次 AllReduce 同步梯度 |
| **DP 通信量** | $2 \times M \times \text{dtype}$，与 batch size 无关 |
| **TP 核心思想** | 层内切分权重矩阵（列切+行切），每层一次 AllReduce |
| **TP 约束** | `num_heads` 必须整除 `tp_size`；强烈依赖高速互联，优先放在单机 NVLink/NVSwitch 域内 |
| **PP 核心思想** | 层间切分，按 stage 传递激活值，存在气泡问题 |
| **PP 优化** | 1F1B、Interleaved 1F1B（Virtual Pipeline）、Zero-Bubble |
| **选型原则** | 模型能放进单卡 → DP；参数放得下但训练状态（梯度/优化器）放不下 → ZeRO-2；连参数都放不下 → ZeRO-3 / FSDP FULL_SHARD 分片参数；单层太大 → TP；层数太多 → PP |
| **混合并行** | DP（跨节点）+ TP（单机内）+ PP（层间）组合使用 |
| **效率排序** | 一般而言通信开销 DP < PP < TP（即通常 DP 效率最高、TP 最吃带宽），但实际表现还取决于模型规模、卡间互联与并行度配置 |

---

## 养成的好习惯

1. **先判断瓶颈维度**——是数据太大还是模型太大？再决定用 DP 还是 MP
2. **优先考虑 DP**——只要模型能放进单卡，一般先用 DP，不急于引入 TP/PP 增加复杂度
3. **TP 尽量不出单机**——张量并行对带宽要求极高，通常应放在单机 NVLink/NVSwitch 域内；确需跨机时，先用基准测试确认通信不会拖垮训练
4. **PP 注意气泡**——流水线并行的 GPU 利用率取决于 micro-batch 数量和调度策略
5. **混合并行先画通信图**——明确 TP 组、PP 组、DP 组的划分，避免通信组冲突
6. **从小规模验证**——先用 2~4 卡验证混合并行逻辑正确，再扩展到大规模集群
