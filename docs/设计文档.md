# AI Agent Trainer 设计文档

## 一、项目概述

AI Agent Trainer 是一个基于多 Agent 协同的个性化学习辅导系统，专注于大模型微调与推理部署领域的教学。系统通过对话式交互生成用户画像，逐阶段推送学习内容，并根据测试结果动态调整学习策略。

当前项目已完成的核心落地点：

- 已统一主库为 `data/sqlite_data/project.db`
- 已落地知识板块与知识点两层知识图谱
- 已落地 `graph_data` 图谱结果层与运行时图文件
- 已将 Agent4 与 Agent5 合并为统一审核代理
- 已接入 `test_questions` 主数据层，供阶段内抽题使用
- 知识文档与向量检索链路已接入，内容覆盖率仍可继续补充
- Agent1 已接入独立的轻量中文语义索引，补足知识板块与子知识点映射的召回能力

## 二、系统架构

### 2.1 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        Frontend (React)                     │
├─────────────────────────────────────────────────────────────┤
│                      API Layer (FastAPI)                    │
├─────────────────────────────────────────────────────────────┤
│                    Orchestrator (Harness)                   │
├─────────────────────────────────────────────────────────────┤
│            Agent1  Agent2  Agent3  Agent4  Agent6          │
├─────────────────────────────────────────────────────────────┤
│                      Tools Layer                            │
├─────────────────────────────────────────────────────────────┤
│                     Skills Layer                            │
├─────────────────────────────────────────────────────────────┤
│      SQLite    ChromaDB    NetworkX    Ollama/DeepSeek      │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 Agent 架构

| Agent | 名称 | 职责 | 核心功能 |
|-------|------|------|----------|
| Agent1 | 学情诊断与阶段选路 | 用户画像与当前/下一阶段生成 | 表单事实解析、别名+语义混合召回、候选内盲区细化、置信度计算、直接先修插入、`generate_stage` 选路 |
| Agent2 | 路径规划逻辑角色 | 阶段规划方法论 | 当前 Harness 不直接实例化 Agent2；其运行时调用由 Agent1 的 `generate_stage` 承担 |
| Agent3 | 内容生成 | 学习资料生产 | 教程生成、代码示例、阶段内答疑、抽取测试题 |
| Agent4 | 统一审核 | 技术与教学质量审核 | 幻觉检测、规则校验、难度分析、认知负荷、风格适配 |
| Agent6 | 阶段决策 | 画像更新与策略选择 | 正确率分析、画像更新、下一阶段策略选择 |

说明：

- 原 Agent5 已并入 Agent4，当前不再作为独立运行代理
- Agent3 负责按 `block_id` 从 `test_questions` 抽取 1~3 道题
- Agent6 负责依据阶段结果更新画像与阶段推进，不负责出题
- Agent6 不重新推断 Agent1 的板块映射，只保留映射元数据并更新学习状态

### 2.3 数据流

```
用户输入 → Orchestrator → Agent1（事实解析 + 混合召回）→ 用户画像
                                                     ↓
                         Agent1.generate_stage（逻辑 Agent2）→ 当前阶段 / 当前知识点
                                                                     ↓
                                                                  Agent3 → 学习包
                                               ↓
                                      Agent4（统一审核）
                                               ↓
                                    Orchestrator → 用户展示
                                               ↓
                              用户问答 / 用户答题 / 阶段完成
                                               ↓
                                            Agent6 → 更新画像与策略
                                               ↓
                         用户确认后 Agent1.generate_stage → 下一阶段
```

## 三、数据层设计

### 3.1 数据分层

| 数据层 | 存储位置 | 作用 |
|--------|----------|------|
| Seed 原始结构化数据 | `data/seeds/` | 维护知识板块、知识点、测试题等原始种子数据 |
| 图谱结果层 | `data/graph_data/` | 存储知识图谱节点、边、派生结果与运行时图文件 |
| 主业务库 | `data/sqlite_data/project.db` | 存储运行期主数据、会话、用户状态和测试题 |
| 向量检索层 | `data/chroma_db/` | 存储 Agent1 专用知识文档语义索引 |
| 原始教学材料 | `data/knowledge_base/` | 存储教程、代码示例、最佳实践等原始内容素材 |

### 3.2 当前知识图谱实现边界

当前阶段知识图谱仅保留两类节点：

- `block` 节点：15 个知识板块
- `subtopic` 节点：68 个知识点

当前已使用的主要边类型：

- `CONTAINS`：板块包含知识点
- `PREREQUISITE_OF`：前置依赖关系
- `PROGRESSES_TO`：同层级的学习推进关系

说明：

- 图谱层存的是“关系结果”，不是原始教学正文
- 原始名称、描述、时长等结构化内容仍以 seed / SQLite 为准
- Agent1 的运行时阶段选路读取 SQLite 主数据，并以 `graph_data` 的关系作为约束；此能力在逻辑职责上对应 Agent2 的路径规划

### 3.3 `graph_data` 当前目录职责

- `data/graph_data/current/nodes.jsonl`：当前图谱节点清单
- `data/graph_data/current/edges.jsonl`：当前图谱边清单
- `data/graph_data/current/manifest.json`：图谱构建说明与元数据
- `data/graph_data/current/derived/`：闭包、层级、校验报告等派生结果
- `data/graph_data/runtime/knowledge_graph.gpickle`：运行期图文件，供后端工具直接读取

### 3.4 `chroma_db` 当前职责

当前 collection 分工：

- `agent1_knowledge_docs`：Agent1 对 `knowledge_docs` 的板块/子知识点候选召回，使用独立的 FastEmbed `BAAI/bge-small-zh-v1.5`、512 维和 cosine 距离

适合进入向量库的数据：

- Agent1 的知识文档、板块说明、子知识点摘要与封闭域检索提示
- 长文本教程切片后的检索片段（若后续需要做 RAG）

当前不适合直接进入向量库的数据：

- 知识板块 / 知识点主键关系
- 学习先后顺序、前置依赖、包含关系
- 会话状态、阶段状态、用户画像
- 测试题判分规则本体

边界划分：

- `graph_data` 负责“关系推理约束”
- `chroma_db` 负责“语义相似检索”
- `project.db` 负责“结构化主数据与运行时状态”

### 3.5 Agent1 映射边界

- 用户明确填写的 `grade`、`skill_tags`、`goal`、`daily_hours`、`learning_style`、`hardware` 是画像事实源，LLM 不得改写
- Agent1 先合并别名精确匹配与 Agent1 专用语义召回，再把候选板块、描述、难度、先修和子知识点上下文交给 LLM 细化
- LLM 只能选择候选中已有的 `block_id` 与 `target_subtopic_ids`；候选证据不足、目标属于目录外领域或 LoRA 语义歧义时，返回低置信度追问，不生成阶段
- `KnowledgeGap.block_id`、`block_name`、`target_subtopic_ids`、`mapping_confidence` 由 Agent1 生成并供其阶段选路使用；Agent6 只更新学习状态相关字段并保留这些映射元数据
- 板块级 `prerequisites` 与子知识点级直接先修分别处理：未掌握的直接板块先修会插入为前置 gap，子知识点先修用于精细选路，不展开为传递闭包

### 3.6 当前主表说明

当前 SQLite 主库中的关键表包括：

- `knowledge_blocks`
- `knowledge_subtopics`
- `subtopic_status`
- `test_questions`
- `sessions`
- `session_states`
- `user_profiles`
- `review_traces`
- `learning_package_sources`
- `learning_package_claims`
- `review_debate_issues`
- `review_debate_rounds`
- `review_debate_responses`

说明：

- `subtopic_status` 是当前真实学习进度状态源
- `knowledge_gaps` 仍保留画像意义，但阶段推进以 `subtopic_status` 为准
- `test_questions` 已进入主数据层，供 Agent3 在阶段中调用
- Agent3 / Agent4 的辩论式审核链路由 `review_traces` 到 `review_debate_responses` 六张表承载
- 详细协议见 `docs/Agent34审核辩论协议.md`

## 四、API 设计

### 4.1 对话接口

- `POST /api/chat/` - 初始对话
- `POST /api/chat/question` - 处理用户问题

### 4.2 会话接口

- `POST /api/session/` - 创建会话
- `GET /api/session/{session_id}` - 获取会话

### 4.3 阶段接口

- `POST /api/stage/start` - 开始阶段
- `POST /api/stage/submit-answer` - 提交答案
- `POST /api/stage/complete/{session_id}` - 完成阶段
- `POST /api/stage/plan-next` - 用户确认后规划下一阶段

### 4.4 可视化接口

- `GET /api/visualize/profile/{session_id}` - 获取画像数据
- `GET /api/visualize/stage/{session_id}` - 获取阶段数据
- `GET /api/visualize/progress/{session_id}` - 获取进度数据

## 五、核心流程

### 5.1 首次输入流程

1. 用户输入学习背景、目标、时长、偏好
2. Orchestrator 提取原始数据
3. Agent1 以表单字段为事实源生成画像，并通过别名+语义混合召回得到受约束的知识盲区
4. 置信度达标后，Agent1 的 `generate_stage` 基于知识图谱与当前状态生成下一阶段；低置信度则返回追问
5. 前端展示画像和阶段信息

### 5.2 学习阶段流程

1. 用户点击“开始学习”
2. Agent3 生成学习包 V1，并输出 `sources` 与 `claims`
3. Agent4 基于 `claims + sources` 执行统一审核
4. 如有错误，Agent3 按 `issue` 逐条回复并修改
5. Agent4 对回复做复核，Orchestrator 记录辩论轮次与裁决
6. 循环直到审核通过或达到最大迭代次数
7. 审核通过则展示正式包；若超轮次则以 `needs_human_review/provisional` 展示临时包

### 5.3 答疑流程

1. 用户提问
2. Agent3 结合知识文档检索与当前阶段上下文调用本地 LLM 生成回答
3. Agent4 对回答做统一审核
4. 通过后展示给用户

### 5.4 测试与迭代流程

1. 用户进入当前阶段测试
2. Agent3 按当前 `block_id` 抽取 1~3 道题
3. 用户提交答案
4. Orchestrator 计算正确率
5. Agent6 更新画像、策略与阶段结果
6. 用户确认继续后，Agent1 的 `generate_stage` 规划下一阶段

## 七、配置说明

### 7.1 环境变量

```env
APP_NAME=AI Agent Trainer
APP_HOST=0.0.0.0
APP_PORT=8000

OLLMA_BASE_URL=http://localhost:11434
OLLMA_MODEL=deepseek-r1:7b

DEEPSEEK_API_KEY=your-api-key
DEEPSEEK_API_BASE=https://api.deepseek.com

DATABASE_URL=sqlite:///../data/sqlite_data/project.db
CHROMA_PATH=../data/chroma_db
GRAPH_PATH=../data/graph_data/runtime/knowledge_graph.gpickle

LOG_LEVEL=INFO
DEBUG=false

MAX_REVIEW_ITERATIONS=3
CONFIDENCE_THRESHOLD=0.7
EXECUTION_MODE=hybrid
```

### 7.2 运行模式

- `deterministic`：不依赖 Ollama，可跑通确定性闭环测试
- `hybrid`：状态管理与阶段推进确定性执行，教程与答疑由模型生成

## 八、部署说明

### 8.1 开发环境

```bash
# 安装依赖
pip install -r requirements.txt

# 初始化主库与知识数据
python scripts/init_db.py
python scripts/init_knowledge_base.py
python scripts/init_agent1_semantic_index.py
python scripts/build_knowledge_graph.py
python scripts/seed_test_data.py

# 校验 Agent1 中文语义召回
python scripts/evaluate_agent1_retrieval.py

# 启动后端
cd backend
python main.py
```

Agent1 索引首次初始化会缓存约 90MB 的 FastEmbed 模型至 `data/fastembed_models/`，CPU 运行时通常额外占用约 200MB 内存，并写入 `data/chroma_db/agent1_knowledge_docs`。这是开发/部署步骤；面向普通用户的发行包应预置缓存与索引，运行时不隐式下载模型。

### 8.2 前端开发

```bash
cd frontend
npm install
npm run dev
```
